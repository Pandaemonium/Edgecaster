SLICE 5 — GAME.PY DECOMPOSITION (NEW — PRIORITY)
===============================================================================

STATUS: game.py is ~5300 lines (drifts over time) and has become the primary bottleneck for
maintainability. This slice defines a surgical decomposition strategy.

GOAL: Reduce game.py to ~1500-2000 lines by extracting cohesive subsystems
into dedicated modules. Game class remains the orchestrator but delegates
to specialized systems.

-------------------------------------------------------------------------------
PHASE 0: ACTION EXECUTION UNIFICATION (~250 lines -> systems/action_runner.py)
-------------------------------------------------------------------------------
Lines: queue_actor_action / _monster_act (plus confirmations + wand/charge plumbing)
Dependencies: systems/actions.py (ActionDef registry), systems/turns.py, urgent-message confirmations

Extract / centralize into a single runner:
- Resolve action def + base delay (action_delay)
- Determine origin (actor vs held/equipped item) for cooldowns/charges
- Gate on cooldowns/charges, emit feedback
- Run confirmations (urgent message) for risky actions (e.g. self-damage)
- Consume charges (wands) and auto-unequip when empty
- Apply cooldowns to the origin
- Apply delay modifiers (slow multipliers, buffs) and clamp (avoid 0-tick loops)

Target module: edgecaster/systems/action_runner.py
Interface: ActionRunner.run(game, actor_id, action_name, **kwargs) -> delay_used

Notes:
- Today the player path (queue_actor_action) and AI path (_monster_act) diverge; unify to prevent bugs.
- After extraction: Game.queue_actor_action becomes a thin wrapper; AI chooses an action then calls ActionRunner and schedules by the returned delay.

1. [LOW RISK]    Phase 10: Params       - self-contained, no side effects
2. [LOW RISK]    Phase 5: Legendaries   - mostly queries, low coupling

6. [MEDIUM RISK] Phase 2: Inventory     - recursive containers need care
7. [MEDIUM RISK] Phase 6: Patterns      - activation state is shared

9. [HIGH RISK]   Phase 4: Overmap       - threading, caching complexity
10. [HIGH RISK]  Phase 8: Zones         - hub module, many dependencies
11. [HIGH RISK]  Phase 7: Combat        - core game loop integration

-------------------------------------------------------------------------------
MIGRATION STRATEGY
-------------------------------------------------------------------------------

For each phase:

1. Create new module with empty class/functions
2. Copy method bodies, adjusting 'self' → 'game' parameter
3. Add thin wrapper in Game that calls the new module
4. Run tests / manual play to verify
5. Delete old method body, keep wrapper OR inline the call
6. Repeat until phase complete

Testing checklist per phase:
- [ ] New game starts without crash
- [ ] Save/load round-trips correctly
- [ ] Affected mechanics work (spawn, inventory, combat, etc.)
- [ ] No import-time errors or circular imports
