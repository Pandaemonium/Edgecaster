EDGECASTER ARCHITECTURE GUIDE
Updated: 2026-04-20

This document orients new contributors to the current structure.
Goal: keep responsibilities clean and make new features easy to add.

===============================================================================
1) HIGH-LEVEL BOUNDARIES

SCENES (edgecaster/scenes/)
- Own UI state + flow, and interpret GameCommand/MenuInput.
- Do scene transitions/stacking via SceneManager.
- Declare visual effects by NAME (but do not implement simulation rules).
- Do not do low-level rendering or camera math.
- `edgecaster/scenes/manager.py`: scene stack, shared options, keybinding load, and audio coordination hub.
- `edgecaster/scenes/base.py`: Scene / PanelScene / PopupMenuScene framework, visual-profile-aware event unprojection, and widget routing.
- `edgecaster/scenes/game_input.py`: pygame event -> `GameCommand` translation and persisted keybinding handling.
- `edgecaster/scenes/dungeon.py`: main live gameplay scene. Owns `DungeonUIState`, command routing, targeting state, hover previews, and most scene pushes during play.
- `edgecaster/scenes/blade_editor_scene.py`: V1 Fractal Blade editor.
  - Open via `open_blade_editor` command (default `B`) or knife context action in inventory.
  - Edits Blade-class intrinsic blade profile only in V1.
  - Immediate apply on each edit; `Esc/Cancel` restores entry snapshot.

INVENTORY / LOOK SCENES (edgecaster/scenes/inventory_scene.py)
- Purpose: a two-pane "inspect + manipulate" UI for an entity.
  - Left pane: inventory list / container navigation (supports nesting into sub-containers).
  - Right pane: embodied preview (glyph/sprite) + body-plan node skeleton overlay + equip-slot interaction.
  - Owner lookup and nested-container consumption now prefer the shared
    inventory/runtime query path (`get_inventory(...)`, runtime entity lookup,
    `remove_inventory_item_at(...)`) instead of treating `game.inventories` as
    authoritative storage.

- Two zoom systems (both intentionally supported):
  1) Diagrammatic zoom (scene open/close):
     - The entire inventory UI eases in/out, anchored to the source glyph (world glyph or parent-inventory glyph).
     - UI panels fade, but the entity preview glyph/sprite is drawn at full opacity for the full transition.
     - Goal: match the settled framing exactly at the end of the transition (no scale/position discontinuity).

  2) Deep body zoom (subnode dive):
     - Double-click body nodes to "dive" (body -> arm -> hand -> finger...) with smooth camera center/scale animation.
     - Invariant: preview glyph/sprite and node skeleton must remain aligned across zoom depth.
     - Shared read surface: `systems/body_view_queries.py` now owns the
       entity-backed zoom/view helpers so Inventory Scene no longer has to own
       a separate graph/schema fallback ladder for this path.
     - Entity-backed zoom helpers now synthesize schema-shaped view data from
       body-node entities and carry explicit `zoomable` metadata so UI labels do
       not need to re-resolve authored schemas just to decide whether a node is
       a branch root.
     - Authored-schema fallback paths now annotate that same `zoomable`
       metadata before returning view data, so label rendering and double-click
       zoom decisions can stay on the shared query surface even when the
       realized body tree is absent.
     - When realized body-node entities are unavailable, those same helpers now
       fall back to deterministic `entity_body` child specs before dropping to
       authored schema traversal, which keeps more of the zoom/view pipeline on
       the shared body substrate in tests and other non-realized contexts.
     - [LEGACY_DELETE][ENTITY_CHAKRA][PHASE_8] This zoom path currently traverses
       authored `body_schema` directly. Migration target: replace with entity-graph
       geometry queries (`entity_body.py` / `entity_geometry.py`) so the body subtree
       and the UI view share one authoritative layout source.

- Key internal contract:
  - BodyViewState: single authoritative bundle of body-view camera state + projected node positions.
  - PreviewCameraCache: caches the LoD0 framing used to make diagrammatic zoom land pixel-identically on the settled view.

- Interaction architecture:
  - Widgets do not control scene transitions directly. They emit "pending" requests (open container, zoom into node,
    activate node context menu). InventoryScene flushes these because it owns the SceneManager.
  - Single-click actions may be delayed to let double-click win; pending actions are flushed even without new input
    events so delayed clicks still fire.

- Slot identity:
  - Equip slots are canonicalized by prefixing the current zoom path so node-local IDs remain stable across depth.

CHAKRA SCENE (edgecaster/scenes/chakra_scene.py)
- Owns chakra selection UI, realign mode, preview widgets, and commit/cancel flow.
- Chakra rules still belong to systems; this scene is the presentation/control surface around them.
- Body-node structure reads now prefer realized body entities and then shared
  `entity_body.build_body_node_specs(...)` output before falling back to schema
  walkers, which narrows the old body-schema-only UI path.
- Live scene reads now prefer `chakra_items.effective_chakra_view(...)` rather
  than materializing a legacy actor-side facade for ordinary UI display.
- Runtime structural reads that should ignore equipped-item overlays now prefer
  `chakra_items.structural_chakra_projection(...)` /
  `chakra_items.structural_chakra_view(...)`, which are component-first and
  no longer consult any cached `actor.chakra_state` bridge.
- Actor chakra write helpers mutate `ChakraComponent` authority directly; the
  old `actor.chakra_state` compatibility cache has been deleted.
- Actor baseline-root inference now prefers shared `entity_body` specs over the
  old baked `body_schema` attribute, and actor-facing chakra reads suppress the
  temporary `{entity_id}:core` placeholder when a real body root is available.
- Realign mode now uses an explicit scene-local `ChakraEditSession` snapshot:
  preview/drag edits mutate that local session and commit back through explicit
  component writes, rather than treating a live runtime state object as the
  editing surface.
- Pattern-root selection and realign commits now route through shared
  `chakra_items` write helpers (`set_actor_chakra_pattern_root(...)`,
  `set_actor_chakra_alignments(...)`) instead of mutating compat tags directly
  from the scene layer.

RENDERERS (edgecaster/render/)
- Pure view layer ("TV unplug test"): if the renderer is removed, the game should still run.
- Do not read input events, mutate game state, or re-implement game rules.
- Renderer draws from scene-owned UI state (e.g. aim predictions, previews).
- `edgecaster/render/ascii.py`: primary dungeon/world renderer. Still large and transitional; some UI/camera bridge state remains here, so edits have broad blast radius.
- Canonical coordinate helpers live in `ascii.py` (`screen_to_abs_tile`, `screen_to_abs_tile_int`, `abs_tile_to_screen_px`) and should replace ad hoc tile/screen math.
- `edgecaster/render/overmap_lod.py`: snapped overmap LoD helper for zoomed-out terrain rendering.
- `edgecaster/render/terrain_tiles.py`: terrain-surface bank/helper code for tiles mode.

SYSTEMS (edgecaster/systems/)
- Where gameplay/simulation logic lives.
- Prefer adding new mechanics as a system module and calling it from Game or a Scene.

STATE (edgecaster/state/)
- Dataclasses / persistent state containers (World, Actor, Entity, etc.).
- `Entity.abs_pos` is canonical. `Entity.pos` is a loaded-zone/local cache.
- `Entity.footprint_local` and `Entity.footprint_abs` are the canonical footprint fields
  (float64 tile-coordinate rectangles). These replace point-based geometry for entities that
  occupy area. `footprint_follows_pos` keeps them in sync with `abs_pos` automatically.
- `World` is a local tile cache for a loaded level, not the whole-world ontology. Legacy
  rectangular zones are cache/projection structures, not the ground truth for what exists.
- The unified hierarchical entity graph (`edgecaster/state/entity_graph.py`) is the
  write-first authority for containment and ownership relationships between entities.
  Other parallel stores (zone entity dicts, inventory lists, attention bins) are transitional
  caches that read from or are kept in sync with the graph; they are marked `[LEGACY_DELETE]`
  and will be removed once graph queries are the sole authority path.
- `POISpec` / `ABSRect` in `state/pois.py` are ABS-space truth for POI definitions.
- `LevelState` still lives in `game.py` as a migration holdout rather than in `edgecaster/state/`.

CONTENT (edgecaster/content/*.yaml, edgecaster/content/*.py)
- Data-driven prototypes and placements.
- Prefer adding new entities/enemies/POIs here instead of hardcoding in code.
- Prototype-bucket inputs currently include: `entities.yaml`, `enemies.yaml`, `anatomy.yaml`, `biology.yaml`, `quests.yaml`, and `site_types.yaml`.
- Dedicated loaders/registries handle POIs, factions, merchants, sealing runes, rune-anchor sieges, and dialogue/NPC fallback metadata.
- Prefer prototype-driven content over adding more parallel fallback definitions to `content/npcs.py` unless the fallback is genuinely still needed.

===============================================================================
2) INPUT + KEYBINDINGS

Single conversion point:
- edgecaster/scenes/game_input.py: Pygame Event -> GameCommand

Keybindings:
- Stored in project root: edgecaster/keybindings.json
- Loaded/owned by SceneManager: edgecaster/scenes/manager.py
- Editable in UI: edgecaster/scenes/keybinds_scene.py (Options -> Controls)

To add a new bindable action:
1) Add it to DEFAULT_BINDINGS in edgecaster/scenes/game_input.py
2) Add it to the keybinds UI grouping/list so it appears in the Controls menu
3) Route the resulting GameCommand in the relevant Scene

Rule: Do not create "hardwired keys" in scenes. If it is a player-facing action,
it should have a keybinding entry so it automatically appears in the keybind menu.

Modifier normalization:
- _normalize_mods() converts left/right modifier variants to their combined form
- KMOD_LSHIFT and KMOD_RSHIFT both normalize to KMOD_SHIFT (same for CTRL, ALT)
- This ensures Shift+C works regardless of which Shift key is pressed

===============================================================================
3) CAMERA + ZOOM (ONE CAMERA INVARIANT)

Camera lives in:
- edgecaster/camera.py

Rules:
- There is ONE canonical camera for all zoom levels.
- Camera owns zoom/pan and world<->screen transforms.
- Renderers consume camera transforms but do not implement them.

===============================================================================
4) MAP GENERATION + OVERMAP + CORRUPTION

Local map generation:
- edgecaster/mapgen.py generates overworld zones (depth 0) and basic dungeon zones.
- edgecaster/biome.py centralizes biome definitions shared by local and overmap rendering.

Climate / Biome System:
- edgecaster/climate.py: 21-biome Whittaker-style classification, ClimateConfig params,
  temperature/wind/moisture field computation. Core exports: Biome enum, classify_biome().
- game.py owns ClimateConfig; systems/overmap.py passes it via overmap_params.

Site placement and realization:
- edgecaster/systems/site_placement.py: deterministic site placement from world fields and site types.
- edgecaster/mapgen_sites.py: site and lair realization helpers once a placed site is concretized.
- edgecaster/content/site_types.yaml: site taxonomy, tags, and placement/realization inputs.
- `mapgen_sites.py` is mixed: legendary lair generation is current/useful, but several site-realization paths are stale or transitional and should be treated carefully.

Overmap / world map rendering:
- Orchestration + background rendering thread: edgecaster/systems/overmap.py
- Fast numeric rendering path: edgecaster/overmap_accel.py (numpy)
- Important invariant: overmap fast paths, scalar/canonical mapgen rules, and climate-aware local generation must stay aligned. Drift here produces map/local semantic mismatches.

Corruption:
- Pure distortion math/LUTs: edgecaster/corruption.py
- Overmap system applies corruption consistently to both global and local sampling.

Rule: avoid drift between "fast path" and "fallback path". If you change corruption
or sampling rules, update both the numpy accelerator and the scalar fallback, or
refactor so there is only one shared implementation.

5) GAME ORCHESTRATOR VS SYSTEM MODULES

game.py should stay relatively thin: it is the orchestrator and state holder.
Most mechanics should live in edgecaster/systems/*.

Current concern map (authoritative):
- `edgecaster/game.py`
  - Orchestration/lifecycle glue only (zone bootstrapping, top-level flow, cross-system coordination).
  - Holds persistent game state and delegates to systems.
  - Maintains incremental zone prewarm queue (`_zone_prewarm_queue`) so neighbor chunk creation is
    budgeted across ticks instead of forced in one frame.
- `edgecaster/systems/spawning.py`
  - Template loading, entity/actor spawn helpers, biome-aware enemy selection,
    debug inventory conjure pipeline.
- `edgecaster/systems/inspection.py`
  - Look/examine logic for tile/entity/terrain descriptions, including ABS-space lookups.
  - Distant ABS tile descriptions now query the shared `SpatialIndex` before
    falling back to legacy `WorldEntityIndex` / `AttentionCellStore` lookups.
- `edgecaster/systems/coords.py`
  - Canonical ABS <-> (zone, local) transforms and coordinate helpers.
- `edgecaster/systems/entity_ops.py`
  - Shared runtime entity query surface (`get_actor`, `get_entity`, `resolve_entity`,
    `iter_actors`, `iter_entities`) plus actor/entity tile queries, blocking checks,
    status mutation helpers, and door toggle behavior.
- `edgecaster/systems/render_query.py`
  - Render-candidate sizing heuristics, entity_ops-backed spatial bin rebuild,
    zone-window clamp helper.
- `edgecaster/systems/attention.py`
  - Attention-driven render candidate assembly (`renderables_in_abs_rect` core path).
  - World proxy staging delegates for sites/POIs/aggregates.
  - Zone-time aggregate detail realization bridge.
  - Attention-staged entities now mirror into the shared `SpatialIndex` as
    `realization_state="staged"` entries while `AttentionCellStore` remains the
    public compatibility store.
  - `sync_attention_instantiation(...)` now short-circuits when the camera view and
    LoD are unchanged and no loaded level is `spatial_dirty`, which keeps the
    advance-time safety-net call from redoing the full realization walk every tick.
  - [LEGACY_DELETE][ENTITY_CHAKRA][PHASE_8] `AttentionCellStore` and the delegate
    methods on `Game` are a transitional bridge. The end-state is a shared
    realization/index path driven directly by entity-graph queries.
- `edgecaster/systems/spatial_index.py`
  - Shared ABS-space rect index for entity lookups across realization states.
  - Tracks `entity_id`, rect, depth, `realization_state`, optional
    `semantic_id`, `kind`, and mirror `source`.
  - Query helpers support filtering by `source`, `realization_state`, and
    `kind`; `query_tag(...)` is the tag-discovery surface for content and
    dialogue callers.
  - Currently mirrors `AttentionCellStore` staged entities and
    `WorldEntityIndex` proxy entities, plus POI specs from `POIRegistry`;
    inspection/distant-look, render candidate, attention warm-window,
    spatial-music, legendary-lair, rune-anchor id, and dialogue site-location
    queries now try this shared index before falling back to legacy
    store-specific queries.
- `edgecaster/systems/zones.py`
  - Mechanical zone/chunk transitions only (no gameplay rituals).
  - Explicit transitions (stairs/fast travel/edge wrap) now trigger a small prewarm slice around
    the destination to reduce first-step hitching after transition.
- `edgecaster/systems/poi_worldgen.py`
  - Runtime POI realization for loaded levels (POI structures, POI NPC spawns, lair/ruin content).
  - Owns `spawn_poi_contents`; `poi_spawning.py` facade deleted in Phase 8.
  - Its orchestration logic currently sits outside the canonical entity-graph resolver and is
    slated to be folded into the unified realization pipeline in a future phase.
- `edgecaster/systems/poi_registry.py`
  - Transitional semantic/content-state registry for POI specs.
  - Spatial lookup is moving to `SpatialIndex`: the registry mirrors POI specs
    into the shared index as collapsed `source="poi_registry"` entries, and
    its remaining zone/rect/point query helpers now delegate to that shared
    index when attached while the registry remains responsible for POI
    content-state persistence.
- `edgecaster/systems/ambient_spawns.py`
  - Active-window ambient hostile population maintenance (tier-aware top-up over time).
  - Called from `Game._advance_time` after per-level scheduling ticks.
- `edgecaster/systems/combat_actions.py`
  - Runtime simulation for action-heavy combat abilities (Wind Rush, Energy Kick,
    Palm Burst, Mirror Strike, Choking Vines, Corrosive Melt, Fern Start,
    Throw Flask, Destabilize, Ignite, Regrow, Freeze, and Wind Rush
    preview/path helpers).
  - `Game` now keeps thin delegate methods for compatibility while the
    implementation lives in this module.
- `edgecaster/systems/blade_runtime.py`
  - Runtime for fractal blade melee (V1): actor blade state, INT-based generator
    slot caps, and verb evaluators for `slash` / `thrust` / `cleave`.
  - Exposes `blade_stat_snapshot(...)` for editor/tooltips so UI and combat share
    one stat source of truth.
  - Owns bump-safe melee execution entry point used by both action handlers and
    movement bump routing (`act_blade_attack`).
  - Keeps hostile-only policy for blade melee centralized to avoid per-verb drift.
- `edgecaster/systems/pattern_runtime.py`
  - Runtime logic for pattern/chakra graph mutation and activation:
    fractal-op application, Activate R/N damage execution, and polygon/star/chakra
    generator actions.
  - Owns chakra resonance/charge helpers used by pattern actions.
  - Runtime modifier calculation now prefers reducer-backed charge snapshots and
    derives resonance from active node ids rather than resolving `body_schema`
    on the hot path.
  - `Game` keeps delegate wrappers (`_apply_fractal_op`, `_activate_pattern_*`,
    `act_polygon`, `act_star`, `act_chakra`, chakra charge/modifier helpers).
- `edgecaster/systems/chakra_effects.py`
  - Data-driven passive effects derived from active chakra conditions.
  - Exposes aggregated effect values (e.g. `fov_radius_bonus`, `move_delay_mult`) so systems query
    one API instead of inspecting chakra node ids ad hoc.
- `edgecaster/systems/damage_policy.py`
  - Central target-filtering rules for damaging effects (self/hostile/neutral/friendly/environment).
  - Replaces ad-hoc per-ability faction checks with declarative `DamagePolicy`.
  - Current migration pass includes: Activate R, Activate N, Throw Flask, Energy Kick, Ignite,
    Freeze, Sparkle, Lightning, Lorenz contact damage, and acidic-pattern tick targeting.
  - Remaining direct single-target combat (`combat.attack`) is intentionally explicit and does
    not require policy iteration.
- `edgecaster/systems/tooltips.py`
  - Action tooltip resolver for ability hover help.
  - Blends static action explanations with live runtime state (targeting, cooldown, charges).
  - Keeps text/logic in systems; scenes only expose hovered action and renderer only draws.
- `edgecaster/systems/rune_anchor_sieges.py`
  - Rune Anchor Siege runtime (auto-start on zone entry, fracture repair, stabilize hold,
    pressure waves, backlash persistence, catastrophe pulse telegraphs/detonations,
    sapper sabotage pressure, and completion dampening reward).
  - Owns encounter state/actions (`anchor_channel`, `anchor_stabilize`, `anchor_purge`)
    and quest compatibility emit.
- `edgecaster/systems/seal_trials.py`
  - Rune Trial runtime and sealing-flow gameplay integration.
- `edgecaster/content/sealing_runes.py` + `edgecaster/content/sealing_runes.yaml`
  - Data definitions for sealing-rune content used by trial/seal systems.

Still in `game.py` and planned for extraction:
- `_make_zone()` once mapgen/POI coupling is reduced.
- `LevelState` definition / ownership remains in `game.py`.

Delegation note:
- `Game.sync_attention_instantiation`, `Game.renderables_in_abs_rect`,
  `Game._ensure_world_site_entities`, `Game._ensure_world_poi_entities`,
  `Game._ensure_world_aggregate_entities`, and
  `Game._realize_aggregate_details_in_zone` are thin delegates into
  `edgecaster/systems/attention.py`.
- The resolver-backed realization path now further delegates to
  `edgecaster/systems/entity_lifecycle.py` for expand/collapse and uses
  `AttentionCellStore`'s hierarchical rect index instead of the older
  single-level ABS bin grid.
- `Game.spatial_index` is now the shared Track-D mirror index. It is created
  before `attn_store` and `world_entity_index`, and both of those legacy stores
  mirror writes into it while callers are migrated.
- `AttentionCellStore` and these delegate methods are transitional bridges
  marked `[LEGACY_DELETE][ENTITY_CHAKRA][PHASE_8]`.
- `AttentionCellStore` still keeps a small fallback dict for compatibility, but
  runtime readers now target its explicit staged-query helper surface (`get`,
  `has`, `ids`) instead of depending on raw `.entities` access.
- Aggregate/detail attention sync now also routes staged child lifecycle
  through explicit helper steps (stage, mirror, promote, drop) instead of
  open-coding store-shaped transitions at each branch.
- `DungeonScene._confirm_look(...)` and `SpatialMusicDirector` now read staged
  / proxy candidates from `SpatialIndex` first, with legacy store-specific
  fallbacks retained until the remaining render/world/POI callers are migrated.
- `attention.renderables_in_abs_rect(...)`,
  `attention.sync_attention_instantiation(...)`, and dialogue site-coordinate
  lookup also read `SpatialIndex` first; their `WorldEntityIndex` /
  `AttentionCellStore` fallbacks are compatibility paths to delete after
  writers directly target the shared realization index.
- `POIRegistry` now mirrors POI specs into `SpatialIndex`; legendary-lair
  lookup, rune-anchor id allocation, and colosseum spatial-music checks are
  SpatialIndex-first with POIRegistry fallbacks where content-state still lives.

Key modules (non-exhaustive):
- systems/actions.py: ActionDef registry (labels, cooldown, cost, etc.)
- systems/action_runner.py: unified action execution (cooldowns, charges, confirmations, delay)
- systems/scheduling.py: event queue and time advance helpers
  Cooldown decay now walks inventory owners/items through the shared
  `inventory.py` query surface instead of iterating `game.inventories`
  directly, so graph-backed and nested container items stay on the same path.
- systems/combat.py: attack resolution + on-death hooks
- systems/inventory.py + systems/equipment.py: inventory, equip/unequip, stat mods.
  `inventory.py` now queries the entity containment graph as the authoritative path.
  The old `game.inventories` parallel containment store has been deleted.
  Shared mutation helpers (`add_inventory_item`, `remove_inventory_item_at`) now centralize
  attach/detach so gameplay/content callers do not hand-roll containment
  mutation and graph patching separately. Shared recursive inventory walkers now live here
  too, so event/system callers do not each keep their own inventory traversal ladders.
- systems/trade.py: merchant pricing + transaction commit.
  Trade reads now also go through the shared inventory query surface for both merchant and
  player inventories, and merchant restock clears old stock through shared detach helpers
  instead of treating the cache list as authority.
- systems/equip_rules.py: item->slot compatibility policy (allowed/blocked slots, prefixes, kinds)
- systems/pattern_ops.py: pattern placement, activation, and pattern-related effects
- systems/targeting.py: aim prediction data (used by renderer only to draw)
- systems/previews.py: non-committing previews for UI
- systems/overmap.py: Julia grid, world map cache/threading, corruption/anchors
- systems/spawning.py: spawn helpers, biome-aware creature selection (tile.biome_id + biome_spawn tags)
- systems/ambient_spawns.py: active-zone population maintenance (Option 2 roaming spawn model)
- systems/entity_snapshots.py: shared persistence bridge for deterministic runtime entities
  (`snapshot_patch_for_entity`, `persist_entity_snapshot`, `apply_entity_snapshot`);
  snapshot writes are now entity_id-authoritative and no longer reinject
  lineage-derived identity into runtime tags during rehydrate. The shared
  snapshot bridge no longer carries `lineage_id` compatibility parameters;
  lineage remains provenance on entity tags rather than part of runtime
  snapshot authority.
- systems/entity_body.py: deterministic actor/body-schema expansion helpers that map authored
  anatomy into a layered entity subtree under the owning actor
- systems/entity_lifecycle.py: resolver-backed expand/collapse lifecycle for attention-managed
  descendants; owns materialization, graph attach/detach, and snapshot writeback on collapse
- systems/entity_geometry.py: shared geometry query envelope + normalized pattern helper used by
  chakra/runtime consumers when component geometry is available
- systems/combat_actions.py: extracted runtime logic for advanced combat actions
  (Wind Rush / Energy Kick / Palm Burst / Mirror Strike / Choking Vines /
   Throw Flask / Destabilize / Ignite / Regrow / Freeze / corrosion + fern toggles)
- systems/blade_runtime.py: extracted runtime logic for Blade-class melee verbs
  (`slash`, `thrust`, `cleave`), actor blade state management, and blade stat snapshots
  consumed by editor/tooltip UI.
- systems/pattern_runtime.py: extracted pattern/chakra runtime execution
  (fractal op mutation, Activate R/N, polygon/star/chakra actions, chakra charge/modifiers)
  `act_chakra(...)` now routes through `chakras.build_chakra_generator_seed_for_actor(...)`
  so runtime casts use the shared actor-backed seed/query surface instead of
  open-coding body-schema fallback.
- systems/poi_worldgen.py: zone-time POI realization policy (structures/NPCs/lair ruin content)
- systems/damage_policy.py: reusable damage target filtering + relation gating
- systems/tooltips.py: action help resolver for ability-bar hover tooltips
- systems/trade.py: trade rules and transaction commit
- systems/reputation.py: faction reputation and hostility hooks
- systems/fern_growth.py: procedural fern pattern growth (coherence-fueled, pruning)
- systems/legendaries.py: legendary registry, lairs, POI discovery/rumors
- systems/lorenz_aura.py: Strange Attractor aura simulation (game-side)
- systems/lighting.py: light emission from entities (illumination, visibility)
- systems/chakras.py: chakra unlock/activation logic, pattern generation
  - The nominal `ChakraState` facade has been deleted. Entity-centric callers
    should query `entity_geometry.py`, `entity_body.py`, or the thinner
    snapshot/query helpers in `chakra_items.py` directly.
  - [LEGACY_DELETE][ENTITY_CHAKRA][BODY_SCHEMA] Recursive body-schema readers inside
    this module are a compatibility bridge; the entity graph backed by
    `entity_body.py` is the forward path.
  - Runtime unlock queries now have a body-node-spec path
    (`list_unlockable_chakras_for_entity`) used by monk level-up and Chakra
    Sage unlock flows, while body-schema traversal remains as a compatibility
    path for editor/pre-runtime callers.
  - A thinner runtime unlock helper
    (`list_unlockable_chakras_for_entity_from_unlocked`) now serves callers
    that only need the current unlocked-node set, avoiding a full
    larger snapshot/view payload for those query-only paths.
- systems/chakra_effects.py: centralized chakra passive-rule evaluation
- systems/chakra_items.py: equipped-item chakra overlays (temporary unlock/auto-active + per-hit modifiers).
  `ChakraComponent` is now the sole write authority. All legacy facade helpers
  (`ensure_actor_chakra_state`, `flush_charges_to_component`,
  `sync_actor_chakra_state`) and the nominal `ChakraState` runtime facade have
  been deleted. Public API entry points are
  `effective_chakra_view`, `effective_chakra_projection`, `effective_active_nodes`,
  `effective_unlocked_nodes`, `toggle_actor_chakra`, `unlock_actor_chakra`,
  `set_actor_chakra_charge`, `tick_actor_chakra_charge`, `consume_actor_chakra_charge`.
  `effective_chakra_view(...)` is the preferred ordinary runtime/UI read, while
  `effective_chakra_projection(...)` remains the thinner dict-shaped variant for
  callers that want primitives without even the lightweight view object.
- systems/body_view_queries.py: shared read-only query surface for body-node rows,
  synthetic zoom schemas, and zoom-path view chains. Chakra Scene and Inventory
  Scene now both route body-view reads through this module instead of each owning
  a separate fallback ladder.
- systems/chakra_reducer.py: [ENTITY_CHAKRA] channel reducer pipeline (R1-R3)
  - reduce_component(comp, rules, dirty_node_ids) computes effective channel values
    (mass, hp, coherence, resonance, corruption, flow, charge) per ChakraComponent node.
  - Rules loaded from content/chakra_rules.yaml (additive/override/max/min combine,
    clamp bounds, edge propagation policies: automatic/none/opt_in).
  - scheduling.chakra_reducer_tick runs this per-tick; result stored as
    actor._chakra_effective_channels for downstream consumers.
  - Active player pattern-channeling is a special hot path: the reducer now
    recomputes directly from component state each tick without paying the usual
    per-tick dirty-mark / subtree-clean graph bookkeeping cost on the expanded
    actor body hierarchy.
  - dirty_node_ids optimization (R2): EntityGraphNode.dirty + mark_dirty_up/
    mark_clean/mark_subtree_clean allow skipping clean edges on future passes.
- systems/rune_audio.py: looped rune drone synthesis for active patterns.
  `sync_rune_drone(...)` now short-circuits when the current pattern signature
  is already playing, instead of re-synthesizing the same loop every frame.
- systems/rune_anchor_sieges.py: failing Rune Anchor gauntlet runtime
  (fracture channeling, wave pacing, stabilize hold, catastrophe pulses, sapper sabotage,
   persistent backlash, corruption dampening completion)
- systems/sites.py: older site-registry path; still present, but no longer the main source of truth for prototype-driven `site_*` placement.

6) VISIBILITY + LIGHTING

FOV (Field of View):
- game.py `_update_fov()` computes which tiles the player can see
- Uses Bresenham LOS checks (`_los()`) from player to each tile in radius
- Equipment can modify view radius via `equip_mods: {view: N}` tag
- Chakra passives can also modify view radius via `systems/chakra_effects.py`
  (currently: active eye chakra grants `fov_radius_bonus=+3`).
- Chakra passives can modify move timing via `systems/chakra_effects.py`
  (currently: active foot chakra grants `move_delay_mult=0.8`, so default move
  cost is 10 -> 8 heartbeats).

Lighting System:
- systems/lighting.py handles light-emitting entities
- Entities with `light_radius > 0` tag emit light
- Light illuminates tiles within radius (with distance falloff)
- Lit tiles become visible if player has LOS to them (even outside FOV radius)
- Optional tags: `light_intensity` (default 1.0), `light_color` (RGB tuple)

Tile State:
- state/world.py `Tile` has: `visible`, `explored`, `illumination`
- `visible`: currently seen this frame
- `explored`: ever seen (for fog-of-war rendering)
- `illumination`: light level from nearby sources (0.0 = dark)

Integration:
- FOV refresh triggered on: movement, zone change, equip/unequip, item drop/pickup
- Lighting calculated after FOV, marks additional lit tiles as visible

11) CHAKRA SYSTEM (BODY-BASED PATTERN GENERATION)

Architectural direction:
- Every chakra IS an entity. The long-term model is that body nodes, chakra activations,
  and their geometry are all first-class entities in the unified entity graph; there is no
  separate "chakra ontology." ChakraComponent records are a migration/cache structure, not
  a permanent second ontology.
- The old runtime `ChakraState` facade has been deleted. New code should pass
  thin snapshot-like payloads (`dict`, `ChakraViewState`, or equivalent) into
  fallback seed/query helpers when it is not already reading from shared entity
  geometry or component-backed query surfaces.
- Body-schema dict traversal (body.root, body.nodes trees) is the legacy representation.
  Entity subtree expansion via entity_lifecycle.expand_entity is the forward path. Both
  paths co-exist during migration; the entity path wins for actors with a realized body tree.

Core module:
- edgecaster/systems/chakras.py: unlock/activation logic, gating checks, pattern generation
  (body-schema traversal inside this module is a compatibility bridge)

Concepts:
- Chakras: body nodes with active/inactive state, aligned with body-schema positions
- Unlocking: chakras must be unlocked before activation; gated by "branch roots" (sub-schema entry points)
- Activation: unlocked chakras can be toggled active/inactive; only active chakras contribute to patterns
- Alignment: per-chakra position offsets for tuning pattern shape
- Pattern generation: active chakra positions become vertices, body tree edges become pattern segments

Gating rules:
- Branch roots are nodes whose prototype defines its own body.root (a sub-schema)
- To unlock a chakra, ALL branch roots in its ancestry must be unlocked
- Example: to unlock "knuckle_2", you need {torso, shoulder, wrist} unlocked (but NOT knuckle_1)

Key functions:
- can_unlock_chakra_for_entity(): checks gating prerequisites (replaces legacy can_unlock_chakra)
- can_unlock_full_chakra_id_from_unlocked(): thin unlocked-set helper for prereq checks without
  building a larger facade snapshot first
- can_unlock_chakra_for_entity_from_unlocked(): thin query helper for UI/scene callers that already
  have an unlocked-node set and want the shared deterministic body-spec gate without mutating state
- list_visible_chakra_nodes_for_entity_from_unlocked(): shared ordered body-spec node list for scenes
  that need the currently unlocked-or-unlockable hierarchy without rebuilding their own local ladder
- unlock_actor_chakra(): unlocks a chakra via component (optionally auto-activates)
- toggle_actor_chakra(): toggles active state via component
- build_chakra_generator_seed_for_actor(): generates canonical seed pattern from active chakras (replaces chakras_to_seed_pattern)
- get_active_chakra_generator_graph_for_entity(): shared actor/body-spec geometry graph read used by
  unexpanded-actor seed fallback paths before dropping to raw schema recursion
- get_gating_chain(): returns list of branch roots needed for a node

UI:
- edgecaster/scenes/chakra_scene.py: ChakraSelectionScene (Shift+C to open)
- Features: body silhouette with glowing chakra points, real-time pattern preview,
  3-layer glow rendering, pulse animations, energy flow lines, particle bursts
- [LEGACY_DELETE][ENTITY_CHAKRA][PHASE_8] ChakraScene still derives layout and
  interaction from body_schema + snapshot-driven fallback walkers. Migration target: replace with
  entity_body/entity_geometry queries once the actor-body graph is the UI authority.
  The pattern preview now receives the live `game` context, so its seed-builder
  path can use shared entity/component geometry during gameplay instead of
  defaulting to schema-only fallback mode.

Chakra pipeline responsibilities (key scripts):
- edgecaster/systems/chakras.py: unlock/activate logic, body-schema traversal (compat),
  world-position projection, and seed pattern generation + metadata. When an actor already
  has a realized body-node tree, the seed builder now prefers that body-entity geometry while
  still honoring the explicit read snapshot for active nodes and pattern root. Generic
  `ChakraComponent` geometry is still queried as an intermediate fallback, and unexpanded
  actors now fall back through deterministic `entity_body.build_body_node_specs(...)` before
  the legacy raw body-schema compatibility path. `get_active_chakra_generator_graph_for_entity(...)`
  now centralizes that shared body-spec graph read, and
  `can_unlock_full_chakra_id_from_unlocked(...)` keeps thin unlock/query callers off
  larger temporary snapshot construction for prereq checks.
  `can_unlock_chakra_for_entity_from_unlocked(...)` gives scene/UI callers the same
  deterministic unlock gate used by runtime unlock flows. `build_chakra_generator_seed_for_actor(...)`
  is now the preferred actor-oriented entrypoint for runtime and scene callers.
- edgecaster/systems/entity_body.py: builds deterministic actor/body subtree specs from the
  authored body schema and drives the layered actor-body expansion path through
  `entity_lifecycle.expand_entity(...)`. This is the authoritative body-node source.
- edgecaster/systems/entity_geometry.py: shared query surface for entity/chakra geometry and
  normalized seed-pattern reconstruction from `ChakraComponent` node/edge data.
- edgecaster/systems/body_view_queries.py: shared scene-query helpers for body-node rows, zoom-path
  schemas/views, unlocked-branch visibility filtering, and UI metadata such as
  branch gating chains and child counts.
- edgecaster/systems/chakra_items.py: runtime effective chakra overlays from equipped items
  (temporary unlocks, auto-activation, and hit-modifier tag parsing).
  `structural_chakra_projection(...)` / `structural_chakra_view(...)` are the
  shared no-item-overlay runtime reads for lifecycle and seed-building callers,
  while `effective_chakra_projection(...)` layers temporary equipment effects
  on top of that structural base. `coerce_chakra_view_state(...)` is now the
  preferred bridge from snapshot-like or dict-like inputs onto this thinner
  query/read model for scenes and runtime helpers.
  Snapshot/bootstrap payloads now normalize through `snapshot_chakra_state(...)`.
- edgecaster/scenes/chakra_scene.py: player-facing UI for selecting/activating chakras, choosing
  the pattern root, and previewing the generated shape (does not apply gameplay effects).
  Pattern preview now uses the same actor-backed seed helper as runtime casting,
  provider/editor inputs are coerced through `chakra_items.coerce_chakra_view_state(...)`,
  and realign-mode preview state is explicitly scene-local `ChakraEditSession`
  data rather than a generic live-state override.
- edgecaster/game.py (act_chakra): applies the chakra generator to the live rune, aligning the
  chosen root and computed terminus to the current segment endpoints.
- edgecaster/patterns/builder.py (CustomGraphGenerator): maps a vertex/edge graph onto a line
  segment baseline (first/last vertices), so root/terminus ordering matters.
- edgecaster/systems/actions.py: registers the "chakra" action and its targeting rules.

Action integration:
- "chakra" action in systems/actions.py: applies chakra pattern as a fractal generator
- Works like Koch/Branch/Custom: transforms existing pattern edges using chakra shape
- Vertex ordering: root (closest to origin) is first, furthest point is last (prevents size explosion)

12) DAMAGE TARGETING POLICY (UNIFIED)

Problem this solves:
- Historically, each ability encoded its own ad-hoc "who can be hit" rules.
- This caused drift (different behavior across similar effects) and duplicated code.

Current model:
- `edgecaster/systems/damage_policy.py` defines `DamagePolicy` and shared evaluators:
  - relation classes: self / hostile / neutral / friendly / environment
  - `iter_damage_targets(...)` for bulk loops
  - `can_damage_target(...)` for single-target checks

Policy examples:
- Activate R / Activate N / Throw Flask: hostile-only, no self.
- Energy Kick / Ignite / Sparkle: broad damageable policy (can include HP-bearing environment),
  excluding self unless explicitly enabled.
- Freeze: actor-only broad policy including self (self-hit intent preserved).
- Lightning / Lorenz / acidic-pattern tick: actor policy with explicit hostility/self semantics.

Cleanup direction:
- Keep damage amounts and effect math local to each ability/system.
- Keep "who can be affected" centralized in `DamagePolicy` so behavior stays consistent.

13) TELEMETRY + PROGRESSION

Telemetry (always-on, separate from debug log):
- `edgecaster/systems/telemetry.py` writes NDJSON events to:
  - `C:\Games\Edgecaster\telemetry.ndjson`
- `Game._telemetry_emit(...)` is the only orchestrator-facing emit API.
- Current emission points:
  - progression: XP gain, level-up, advancement-point spends
  - action execution: success/failure/cooldown/confirm-pending (action_runner)
  - combat: attack resolution, damage hits, XP drains, kills, currency drops

Why this shape:
- Keeps debug logging and gameplay telemetry separate.
- Keeps call-sites lightweight and fail-soft (telemetry must never affect gameplay).
- Makes later telemetry removal easy (delete call-sites + one module).

Level-up advancement model:
- Player gains exactly `+1 advancement point` per level.
- Odd levels: point is auto-spent via weighted random stat roll.
- Even levels: player chooses stat via urgent popup choices (`CON/RES/INT/AGI`).
- Stat spend helper is centralized in `Game._spend_advancement_point(...)`.

Notes:
- Character creation `point_pool` remains separate from runtime `advancement_points`.
- Runtime advancement points persist on `Character.advancement_points`.
