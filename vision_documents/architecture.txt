EDGECASTER ARCHITECTURE GUIDE
High-Level Overview and Refactor Roadmap
Updated: 2025-12-15
Status: Widget system stable; PanelScene foundation stable; major menus migrated

This document orients new contributors to the current structure.
It must remain concise, accurate, and immediately useful.

===============================================================================
SECTION 1 — CORE RESPONSIBILITIES

SCENES (edgecaster/scenes/)
Own:

• Scene-local UI state and flow
• Input interpretation (via GameCommand / MenuInput)
• Scene transitions and stacking (SceneManager)
• Declaring visual effects by NAME
• Declaring which overlay widget layers are active

Do NOT:

• Perform low-level rendering
• Apply pygame transforms directly
• Implement simulation rules

Key scene modules:

manager.py  
– Scene stack + popup/window stack  
– Overlay widget layer service (e.g. "hud")

base.py  
– Scene base types  
– PanelScene (widget-driven foundation)  
– GeneralMenuScene (selection, confirm/cancel, scrolling)  
– MenuFrameWidget (standard banner/body/list/footer layout)  
– Legacy wrappers (MenuScene / PopupMenuScene)

dungeon.py  
– Primary gameplay scene  
– TargetMode flow + UI routing  
– Transitions to inventory / popups

inventory_scene.py  
– Recursive inventories (effect-driven)  
– Implemented as popup PanelScenes during migration

options_scene.py / keybindings_scene.py / character_creation_scene.py  
– Fully migrated to PanelScene + widget-driven layout  
– Mouse + keyboard parity  
– No legacy layout code remains

urgent_message_scene.py / dialogue_scene.py  
– Widget-driven popups with wrapped text + choices  
– Consistent popup underlay handling

IMPORTANT: Avoid importing the scenes package root at module import time.

===============================================================================
SECTION 2 — RENDERING & VISUAL EFFECTS

RENDERERS (edgecaster/render/)
Pure view layer.

ascii.py:
• Draws dungeon, entities, overlays
• Draws panel-local UI for menus/popups
• Applies VisualProfiles and VisualEffects at draw time
• Owns present-stage utilities (screen shake impulses, etc.)

Renderers NEVER:
• Read input events
• Interpret GameCommands
• Store gameplay or UI state

===============================================================================
SECTION 3 — INPUT

INPUT (edgecaster/scenes/game_input.py)

Single conversion point:
Pygame Event → GameCommand

Scenes interpret GameCommands.
Renderers are input-agnostic.

MenuInput:
• Shared keyboard repeat + navigation logic
• Used by all menu / PanelScene flows
• Keyboard navigation yields to mouse movement when mouse is active

===============================================================================
SECTION 4 — VISUAL TRANSFORM & EFFECT PIPELINE

visuals.py:
• VisualProfile (scale, offset, rotation, alpha, flips)
• apply_visual_panel(...) → transforms & blits surfaces
• unproject_mouse(...) → invert transforms for hit-testing

visual_effects.py:
Registry of named VisualEffects (e.g. "clockwise", "ghostly", "fiery", "bismuth")

Effects may modify:
• Geometry lane (rotation/scale/flip/alpha)
• Color lane (tint/flicker)
• Overlay lane (particles, scanlines, shimmer)
• Present lane (shake/vibration impulses)

Rules:
• Effects are stackable and order-preserving
• Duplicate effects intentionally compound
• Scenes/entities declare effect names only

Overlay bounds:
Effects may specify a local rect, enabling localized auras/smoke
without bleeding across the entire screen.

===============================================================================
SECTION 5 — PANELSCENE & WIDGET SYSTEM

Widget foundation (edgecaster/ui/widgets.py):

• WidgetContext(surface, game, scene, renderer)
• Widget base class (layout, draw, handle_event, update)
• Layout containers (VBox/HBox)
• Interactive widgets (Label, Button, List, etc.)
• Wrapped-text widgets (pixel-based, no ellipses)
• Scaled label widgets for title hierarchy

Ownership model:
• Scenes own widget trees
• Input routed to widgets first
• Renderer remains draw-only

PanelScene (edgecaster/scenes/base.py):

• Owns logical panel surface + rect (fullscreen or popup)
• Owns root widget tree
• Routes input to widgets FIRST
• Applies VisualProfiles / VisualEffects consistently
• Converts mouse events to panel-local coordinates

GeneralMenuScene:

Built on PanelScene.
Provides:
• Selection model
• Confirm/cancel behavior
• Scrolling
• Keyboard + mouse arbitration

MenuFrameWidget:
Standard layout:
• Title/banner at top
• Optional body text
• Scrollable list
• Optional footer pinned bottom

===============================================================================
SECTION 6 — POPUPS & UNDERLAY SNAPSHOT (IMPORTANT)

PopupMenuScene behavior:

• Underlay snapshot must represent the scene stack BELOW the popup
• Snapshot rebuilt on first draw
• Renderer.present / _present temporarily suppressed during rebuild
  to avoid visible flicker or “blink back to dungeon”

This logic is centralized and must not be duplicated ad hoc.

SECTION 7 — DATA-DRIVEN ENTITIES

YAML prototypes define:
• parent, glyph, color
• description (inherited)
• stats, tags, behaviors

Runtime entities are fully resolved archetypes.
Look-mode displays inherited descriptions.

Entity tags may include visual_effects names,
which the renderer applies consistently.

Immediate next improvements:
- Normalize menu aesthetics (padding, borders, fonts)
- Two-pane inventory (list + details)
- Keybinds/options unification using widgets

SECTION 8 — ENTITY / INVENTORY / MAP ONTOLOGY

Core conceptual model (important for future work):

• Entities are the fundamental unit of the game world.
• An inventory is not a special container type, but a general expression of
  containment or composition between entities.
• Opening an inventory means inspecting an entity’s internal structure.

This applies uniformly across scales:

• A creature’s inventory may contain items or body parts.
• An equipped item is an inventory item with an attachment relationship
  (rendered visually, not treated as a separate system).
• A dungeon or map is an entity whose inventory is rendered spatially and
  permits movement, time flow, and combat.
• The “main dungeon scene” is simply the currently inhabited spatial inventory.

UI implication:

• Inventory screens, inspection (“look”), and map views are all specializations
  of the same underlying operation: opening an entity.
• PanelScene is the common foundation for these views; differences are expressed
  via permissions, layout, and rendering mode, not separate scene types.

Simulation implication:

• Internal detail may be generated on demand when an entity is opened and
  summarized or discarded when it is closed.
• Fidelity is governed by proximity, narrative importance, and player interaction,
  not by a requirement to simulate all entities continuously.

This ontology is intentional and should be preserved when introducing new UI,
inventory, or world-scale features.

SECTION 9 — MAP GENERATION + CORRUPTION (WORLD / LOCAL COHERENCE)

Core invariant:
- The world map (overmap) and local overworld zones must remain "intimately tied".
  A global world tile (gx, gy) must always map to exactly one Julia-plane coord
  (jx, jy), and both overmap rendering and local zone generation must use that
  same mapping.
