EDGECASTER ARCHITECTURE GUIDE
High-Level Overview and Refactor Roadmap
Updated: 2025-12-14
(Status: Widget system online; PanelScene foundation online; VisualProfile + VisualEffect pipeline active)

This document orients new contributors to the current structure.
It must remain concise, accurate, and immediately useful.

===============================================================================
SECTION 1 — LAYER RESPONSIBILITIES

SCENES (edgecaster/scenes/)
Own:

Input interpretation (via GameCommand)

Scene-local UI state (menus, dialogs, targeting, inventory, ability bar sync)

Scene transitions and stacking (SceneManager)

Declaring which overlay widget layers are active (scene.overlay_layers)

Declaring visual effects by NAME (scene.visual_effects)

Do NOT:

Perform low-level rendering

Apply pygame transforms directly

Implement simulation rules

Key scene modules:

manager.py
- Scene stack + window stack
- Overlay widget layer service ("hud", etc.)

base.py
- Scene base types
- PanelScene foundation (widget-driven)
- GeneralMenuScene (selection, confirm/cancel, scrolling)
- Legacy wrappers (MenuScene / PopupMenuScene) over GeneralMenuScene

dungeon.py
- Primary gameplay scene
- TargetMode flow + UI routing
- Transitions to inventory/popups

inventory_scene.py
- Nested inventories (effect-driven; recursive)
- Built as a (legacy) popup wrapper over GeneralMenuScene during migration

urgent_message_scene.py
- Generic urgent popup/dialog (death/level-up confirmations)
- Built as a (legacy) popup wrapper over GeneralMenuScene during migration

dialogue_scene.py
- Dialogue popups (dialogue trees + callbacks)
- IMPORTANT: avoid importing events/scenes package root at module import time

Other menus:
- options / keybinds / character creation etc.

RENDERERS (edgecaster/render/)
Pure view layer.

ascii.py:
- Draws map, entities, overlays
- Draws panel-local UI for popup/menu scenes
- Applies VisualProfiles and VisualEffects at draw time
- Owns any “present” stage utilities (screen shake impulses etc.)

Renderers NEVER:
- Read input events
- Interpret GameCommands
- Store gameplay or UI state

INPUT (edgecaster/scenes/game_input.py)
Single conversion point:
Pygame Event → GameCommand(kind=...)

Scenes interpret GameCommands.
Renderers are input-agnostic.

GAME CORE (edgecaster/game.py)
Authoritative simulation:
- Entities, actors, stats
- Turn updates, movement, collisions, combat
- Fractal mechanics, patterns, rune interactions
- Procedural world state, RNG

Does NOT:
- Know about rendering
- Contain UI logic or transforms

SYSTEMS (edgecaster/systems/)
Pure logic modules:
- actions.py → Action metadata + targeting specs
- abilities.py → Actor abilities
- patterns/* → Fractal generation
- ai.py → Behavior stubs

===============================================================================
SECTION 2 — VISUAL TRANSFORM & EFFECT PIPELINE

Two distinct but cooperating systems:

visuals.py:
- VisualProfile (scale, offset, rotation, alpha, flips)
- apply_visual_panel(...) → transforms & blits a panel/surface to screen
- unproject_mouse(...) → invert transforms for hit-testing (mouse ↔ rotated/shrunk panels)

visual_effects.py:
Registry of named VisualEffects (e.g. "clockwise", "ghostly", "fiery", "bismuth")

Effects may modify:
• VisualProfile (geometry lane: rotate/scale/flip/alpha/offset)
• Entity draw style (color lane: tint/flicker)
• Final present rect (present lane: screen shake/vibration impulses)
• Surface overlays (overlay lane: particles/shimmer/scanlines)

Rules:
- Effects are stackable and order-preserving
- Duplicate effects intentionally compound (fractal recursion)
- Scenes/entities declare effect names only; all effect behavior lives in visual_effects.py

Overlay bounds:
Effects can optionally specify an overlay drawing rect (local coordinates),
allowing localized auras or rising smoke/embers around a tile/panel without
bleeding across the whole screen.

SECTION 3 — TARGETING (UNIFIED TARGETMODE)

TargetingSpec (actions.py):
- kind: tile | vertex | look
- mode: aim | terminus | inspect
- range parameters

TargetState (scene-local):
- cursor, origin, mode

DungeonScene:
- Owns targeting flow

Renderer:
- Draws cursor only

===============================================================================
SECTION 4 — WIDGET SYSTEM, PANELSCENE, AND MENU MIGRATION

Widget foundation (edgecaster/ui/widgets.py):
- WidgetContext(surface, game, scene, renderer)
- Widget base class (layout, draw, handle_event, update)
- Layout containers (VBox/HBox)
- Interactive widgets (Label, MultiLineLabel, Button, List, etc.)

Ownership model:
- Scenes own widget trees and route input
- Renderer remains draw-only

PanelScene (edgecaster/scenes/base.py):
- Owns a logical panel surface + rect (fullscreen or popup)
- Owns a root widget tree
- Routes input to widgets FIRST (UI priority)
- Applies VisualProfile/VisualEffects consistently via visuals.py + visual_effects.py
- Converts mouse events into panel-local coordinates by inverting the visual transform

GeneralMenuScene:
- Built on PanelScene
- Provides:
  - selection model
  - confirm/cancel behavior
  - scrolling (ListWidget)
  - keyboard + mouse arbitration:
    keyboard navigation “wins” until the mouse moves again

Legacy wrappers:
- MenuScene and PopupMenuScene are thin wrappers over GeneralMenuScene
- Existing menu subclasses should continue to work (functional parity required)
- Visual/aesthetic changes acceptable during transition

Multiline banners:
- Many legacy scenes relied on multi-line ASCII art or header/body text.
- Use MultiLineLabelWidget for banners containing newlines.

Overlay widget layers:
- SceneManager maintains named widget layers (e.g. "hud")
- Scenes opt in via overlay_layers
- Popup dimming occurs before overlays
- Allows live HUD during inventory/popups

HUD widgets:
- status_header.py → StatusHeaderWidget
- ability_bar.py → AbilityBarWidget (wraps AbilityBarRenderer + hit-testing)

===============================================================================
SECTION 5 — DATA-DRIVEN ENTITIES & INHERITANCE

YAML prototypes define:
- parent, glyph, color
- description (inherited)
- stats, tags, behaviors

Runtime entities are fully resolved archetypes.
Look-mode displays inherited descriptions.

Entity tags may include "visual_effects" names; renderer applies these consistently
to glyph color and (optionally) localized overlays on the map.

===============================================================================
SECTION 6 — IMPORT HYGIENE (AVOID CIRCULAR IMPORTS)

Avoid importing heavyweight modules at package import time.
In particular:
- Do NOT make edgecaster/scenes/__init__.py import SceneManager (or other heavy modules).
- Prefer direct imports:
    from edgecaster.scenes.manager import SceneManager
  rather than:
    from edgecaster.scenes import SceneManager

Dialogue/events:
- events.py should not import scenes at module import time.
- dialogue_scene.py should not import events at module import time.
Use local imports inside functions if needed.

SECTION 7 — CURRENT STRATEGIC WORK

The current UI migration order (stay disciplined):
HUD → Ability Bar → generalized MenuScene widgets → Inventory → Keybinds → Options

Immediate next improvements:
- Normalize menu aesthetics (padding, borders, fonts)
- Two-pane inventory (list + details)
- Keybinds/options unification using widgets
- Reduce ad-hoc coordinate math; keep all transforms via VisualProfile/VisualEffects

SECTION 8 - MAP GENERATION + CORRUPTION (WORLD/LOCAL COHERENCE)

Core invariant:
- The world map (overmap) and local overworld zones must remain "intimately tied".
  A global world tile (gx, gy) must always map to exactly one Julia-plane coord
  (jx, jy), and both overmap rendering and local zone generation must use that
  same mapping.

Where this lives:
- edgecaster/game.py
  - game.overmap_params holds the authoritative Julia view extents + chosen c.
  - game.tile_julia_grid precomputes the mapping arrays:
      jx = tile_julia_grid["x"][gx]
      jy = tile_julia_grid["y"][gy]
  - Startup policy: the world map is rendered lazily when opened (pop-in is ok);
    avoid doing heavy overmap rendering work during Game.__init__.

- edgecaster/scenes/world_map_scene.py + edgecaster/overmap_accel.py
  - The overmap is rendered at low resolution and scaled up for display.
  - The default path uses numpy acceleration (`overmap_accel.render_overmap_buffers_numpy`)
    and routes all corruption math through `edgecaster.corruption.distortion_np` so
    the fast path cannot drift from the scalar rules.

- edgecaster/mapgen.py
  - Overworld zones (depth 0) are generated using Julia sampling at per-tile
    coords from tile_julia_grid slices (`jx_slice`/`jy_slice`).
  - A numpy grid fast-path exists for generating full (height, env) arrays for a
    zone without per-tile Python loops.

- edgecaster/corruption.py
  - Corruption modifies the Julia iterator:
      z_{n+1} = z_n^2 + c + d(z_n)
  - d(z) is evaluated via LUT sampling while |z| <= 2; LUTs are cached and
    built with numpy when available (with a pure-Python fallback).
  - Rune anchors are part of the corruption system and suppress corruption
    multiplicatively in the Julia z-plane.

Docs:
- vision_documents/map_generation_strategy.txt is the detailed reference for
  how map generation/corruption are implemented and which invariants to preserve.
