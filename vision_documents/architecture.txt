EDGECASTER ARCHITECTURE GUIDE
Updated: 2026-01-09

This document orients new contributors to the current structure.
Goal: keep responsibilities clean and make new features easy to add.

===============================================================================
1) HIGH-LEVEL BOUNDARIES

SCENES (edgecaster/scenes/)
- Own UI state + flow, and interpret GameCommand/MenuInput.
- Do scene transitions/stacking via SceneManager.
- Declare visual effects by NAME (but do not implement simulation rules).
- Do not do low-level rendering or camera math.

RENDERERS (edgecaster/render/)
- Pure view layer ("TV unplug test"): if the renderer is removed, the game should still run.
- Do not read input events, mutate game state, or re-implement game rules.
- Renderer draws from scene-owned UI state (e.g. aim predictions, previews).

SYSTEMS (edgecaster/systems/)
- Where gameplay/simulation logic lives.
- Prefer adding new mechanics as a system module and calling it from Game or a Scene.

STATE (edgecaster/state/)
- Dataclasses / persistent state containers (World, Actor, Entity, etc.).

CONTENT (edgecaster/content/*.yaml, edgecaster/content/*.py)
- Data-driven prototypes and placements.
- Prefer adding new entities/enemies/POIs here instead of hardcoding in code.

===============================================================================
2) INPUT + KEYBINDINGS

Single conversion point:
- edgecaster/scenes/game_input.py: Pygame Event -> GameCommand

Keybindings:
- Stored in project root: edgecaster/keybindings.json
- Loaded/owned by SceneManager: edgecaster/scenes/manager.py
- Editable in UI: edgecaster/scenes/keybinds_scene.py (Options -> Controls)

To add a new bindable action:
1) Add it to DEFAULT_BINDINGS in edgecaster/scenes/game_input.py
2) Add it to the keybinds UI grouping/list so it appears in the Controls menu
3) Route the resulting GameCommand in the relevant Scene

Rule: Do not create "hardwired keys" in scenes. If it is a player-facing action,
it should have a keybinding entry so it automatically appears in the keybind menu.

===============================================================================
3) CAMERA + ZOOM (ONE CAMERA INVARIANT)

Camera lives in:
- edgecaster/camera.py

Rules:
- There is ONE canonical camera for all zoom levels.
- Camera owns zoom/pan and world<->screen transforms.
- Renderers consume camera transforms but do not implement them.

===============================================================================
4) MAP GENERATION + OVERMAP + CORRUPTION

Local map generation:
- edgecaster/mapgen.py generates overworld zones (depth 0) and basic dungeon zones.
- edgecaster/biome.py centralizes biome definitions shared by local and overmap rendering.

Climate / Biome System:
- edgecaster/climate.py: 21-biome Whittaker-style classification, ClimateConfig params,
  temperature/wind/moisture field computation. Core exports: Biome enum, classify_biome().
- game.py owns ClimateConfig; systems/overmap.py passes it via overmap_params.

Overmap / world map rendering:
- Orchestration + background rendering thread: edgecaster/systems/overmap.py
- Fast numeric rendering path: edgecaster/overmap_accel.py (numpy)

Corruption:
- Pure distortion math/LUTs: edgecaster/corruption.py
- Overmap system applies corruption consistently to both global and local sampling.

Rule: avoid drift between "fast path" and "fallback path". If you change corruption
or sampling rules, update both the numpy accelerator and the scalar fallback, or
refactor so there is only one shared implementation.

===============================================================================
5) GAME ORCHESTRATOR VS SYSTEM MODULES

game.py should stay relatively thin: it is the orchestrator and state holder.
Most mechanics should live in edgecaster/systems/*.

Key modules (non-exhaustive):
- systems/actions.py: ActionDef registry (labels, cooldown, cost, etc.)
- systems/action_runner.py: unified action execution (cooldowns, charges, confirmations, delay)
- systems/scheduling.py: event queue and time advance helpers
- systems/combat.py: attack resolution + on-death hooks
- systems/inventory.py + systems/equipment.py: inventory, equip/unequip, stat mods
- systems/pattern_ops.py: pattern placement, activation, and pattern-related effects
- systems/targeting.py: aim prediction data (used by renderer only to draw)
- systems/previews.py: non-committing previews for UI
- systems/overmap.py: Julia grid, world map cache/threading, corruption/anchors
- systems/spawning.py: spawn helpers for YAML prototypes and POI contents
- systems/trade.py: trade rules and transaction commit
- systems/reputation.py: faction reputation and hostility hooks
- systems/legendaries.py: legendary registry, lairs, POI discovery/rumors
- systems/lorenz_aura.py: Strange Attractor aura simulation (game-side)
- systems/lighting.py: light emission from entities (illumination, visibility)

===============================================================================
6) VISIBILITY + LIGHTING

FOV (Field of View):
- game.py `_update_fov()` computes which tiles the player can see
- Uses Bresenham LOS checks (`_los()`) from player to each tile in radius
- Equipment can modify view radius via `equip_mods: {view: N}` tag

Lighting System:
- systems/lighting.py handles light-emitting entities
- Entities with `light_radius > 0` tag emit light
- Light illuminates tiles within radius (with distance falloff)
- Lit tiles become visible if player has LOS to them (even outside FOV radius)
- Optional tags: `light_intensity` (default 1.0), `light_color` (RGB tuple)

Tile State:
- state/world.py `Tile` has: `visible`, `explored`, `illumination`
- `visible`: currently seen this frame
- `explored`: ever seen (for fog-of-war rendering)
- `illumination`: light level from nearby sources (0.0 = dark)

Integration:
- FOV refresh triggered on: movement, zone change, equip/unequip, item drop/pickup
- Lighting calculated after FOV, marks additional lit tiles as visible

===============================================================================
7) DATA-DRIVEN PROTOTYPES + SPAWN PIPELINE

Prototypes:
- edgecaster/content/entities.yaml: non-actor entities (items, doors, signs, etc.)
- edgecaster/content/enemies.yaml: actor templates (enemies, bosses, some NPC-like actors)
- edgecaster/content/pois.yaml: POI definitions (npcs + structures per zone coord)

Spawn pipeline:
- edgecaster/prototypes.py: parses YAML into prototype objects
- edgecaster/spawn_factory.py and edgecaster/enemies/factory.py: instantiate runtime objects
- edgecaster/systems/spawning.py: higher-level helpers (spawn enemies, POI contents, etc.)

Rule: if you are adding entities like NPCs, item stocks, POI spawns, etc.,
prefer sending them through the prototype/spawn pipeline so instantiation stays consistent.

===============================================================================
8) DIALOGUE

Dialogue model:
- edgecaster/events.py defines DialogueTree / DialogueNode / DialogueChoice
- events.start_dialogue(game, tree, start_node=...) is the entry point

Dialogue UI:
- edgecaster/scenes/dialogue_scene.py renders a node at a time and advances via next_id

Authoring:
- NPC metadata lives in edgecaster/content/npcs.py (NPC_DEFS)
- NPC dialogue trees should be built via a single builder path (avoid ad-hoc talk handlers)

===============================================================================
9) ASSETS, LOGGING, AND TESTING

Assets live in project root:
- assets/icons/* (PNG icons like bismuth)
- assets/sfx/* (SFX like chaching)

Debug log:
- debug.log lives in project root (used by game + renderer debug helpers)

Testing:
- Run tests with: python -m pytest
  (Avoid calling bare "pytest" on PATH because it may point at a different Python install.)

===============================================================================
10) MERCHANTS / TRADING (ARCHITECTURE)

- Trade rules: edgecaster/systems/trade.py
- UI: edgecaster/scenes/merchant_scene.py (PanelScene-style menu)
- Esc cancels a proposal; Accept commits and exits
- Merchant definitions should be data-driven (content YAML) and spawned via POIs where possible

===============================================================================
GUIDING PRINCIPLES

- Prefer architecture over cleverness
- Preserve functional parity before aesthetics
- Let systems compose instead of special-casing
- Keep the geometry weird
