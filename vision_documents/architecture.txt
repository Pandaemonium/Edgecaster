EDGECASTER ARCHITECTURE GUIDE
High-Level Overview and Refactor Roadmap
Updated: 2025-12-22
Status: Widget system stable; PanelScene foundation stable; map zoom refactor complete

This document orients new contributors to the current structure.
It must remain concise, accurate, and immediately useful.

===============================================================================
SECTION 1 — CORE RESPONSIBILITIES

SCENES (edgecaster/scenes/)
Own:

• Scene-local UI state and flow
• Input interpretation (via GameCommand / MenuInput)
• Scene transitions and stacking (SceneManager)
• Declaring visual effects by NAME
• Declaring which overlay widget layers are active

Do NOT:

• Perform low-level rendering
• Apply pygame transforms directly
• Implement simulation rules

Key scene modules:

manager.py  
– Scene stack + popup/window stack  
– Overlay widget layer service (e.g. "hud")

base.py  
– Scene base types  
– PanelScene (widget-driven foundation)  
– GeneralMenuScene (selection, confirm/cancel, scrolling)  
– MenuFrameWidget (standard banner/body/list/footer layout)  

dungeon.py  
– Primary gameplay scene  
– TargetMode flow + UI routing  
– Camera-relative map presentation (renderer-driven)

IMPORTANT: Avoid importing the scenes package root at module import time.

===============================================================================
SECTION 2 — RENDERING, CAMERA, & MAP ZOOM

RENDERERS (edgecaster/render/)
Pure view layer.

ascii.py:
• ASCII rendering for dungeon, overworld, entities, overlays
• Draws terrain at multiple levels of detail (LoD)
• Applies VisualProfiles and VisualEffects at draw time
• Delegates all camera math and LoD policy elsewhere
• Draws previews from scene-owned ui_state (aim_prediction, action_preview)
  - Preview data is computed in edgecaster/systems/targeting.py and edgecaster/systems/previews.py
  - Renderer stays a pure view layer (no simulation rules)

Renderers NEVER:
• Read input events
• Interpret GameCommands
• Store gameplay or UI state

CAMERA (edgecaster/camera.py)

camera.py:
• Owns the canonical tile-space camera
• World position + zoom live here
• Handles:
  – zoom stepping and damping
  – cursor-anchored zoom
  – pan in pixel or tile space
  – world ↔ screen coordinate transforms
• Renderer-agnostic (can drive ASCII, tiles, sprites)

This enforces the invariant:
→ There is ONE camera for all zoom levels.

===============================================================================
SECTION 3 — MULTI-SCALE MAP RENDERING (LoD)

OVERMAP LOD (edgecaster/render/overmap_lod.py)

overmap_lod.py:
• Responsible for zoomed-out terrain aggregation
• Renders a snapped, rigid grid of “LoD cells”
• Each LoD cell summarizes many local tiles:
  – glyph sampling / majority / weighted biome logic
• Handles fade/blend thresholds between:
  – local tiles
  – global (condensed) tiles
• Owns caching keyed by:
  – world region
  – zoom level
  – sampling parameters

Key property:
• LoD tiles do NOT “swim” under camera motion.
  They remain locked to world tile boundaries.

Optional acceleration:
• Uses overmap_accel (numpy) when available
• Scalar fallback remains deterministic

===============================================================================
SECTION 4 — MAP GENERATION & BIOMES

MAP GENERATION (edgecaster/mapgen.py)

mapgen.py:
• Generates local overworld zones (depth 0)
• Uses the same Julia-plane mapping as the overmap
• Converts sampled fields → terrain glyphs/colors
• Supports fast numpy grid paths

BIOMES (edgecaster/biome.py)

biome.py:
• Centralizes biome definitions
• Maps sampled fields → biome indices
• Provides:
  – glyph choices
  – base color/tint
  – biome-level semantics
• Shared by:
  – local zone generation
  – overmap / LoD glyph sampling

This prevents drift between “what the world looks like”
and “what local terrain becomes.”

SECTION 5 — INPUT

INPUT (edgecaster/scenes/game_input.py)

Single conversion point:
Pygame Event → GameCommand

Scenes interpret GameCommands.
Renderers and camera are input-agnostic.

SECTION 5.5 — DIALOGUE (NPC + EVENTS)

  - In normal gameplay this opens DialoguePopupScene via SceneManager
  - In headless/tests it falls back to urgent popups

Dialogue UI (edgecaster/scenes/dialogue_scene.py):
• DialoguePopupScene renders a single node at a time and advances via next_id

NPC dialogue authoring:
• NPC metadata (name/dialogue/etc.) lives in edgecaster/content/npcs.py (NPC_DEFS)
• NPC Talk builds trees in edgecaster/content/dialogues.py (build_npc_dialogue_tree)
  - This is the unified path for all NPC conversations (multi-screen supported)
  - Avoid ad-hoc dialogue handlers (no legacy talk_start/talk_complete); always route through DialogueTree

SECTION 5.6 — AUDIO & MUSIC SYSTEM (SCENE-DRIVEN, STACK-AWARE)

Edgecaster uses a centralized, scene-driven music controller designed to work
with the SceneManager stack model (base scenes + window/overlay scenes).

The key design rule:

• At any moment, exactly ONE "music" track plays.
• Sound effects (SFX) are layered separately and do not affect music state.

-------------------------------------------------------------------------------
OVERVIEW

Music playback is owned by a single AudioManager instance, created and owned by
SceneManager.

File:
edgecaster/scenes/audio_manager.py

SceneManager is responsible for:
• Creating AudioManager
• Registering music keys → file paths
• Synchronizing music when the scene stack changes
• Forwarding pygame music-end events
• Ticking AudioManager each frame

Scenes NEVER load or play music directly.
Scenes only DECLARE intent via attributes.

-------------------------------------------------------------------------------
AUDIO MANAGER RESPONSIBILITIES

AudioManager handles:

• One-at-a-time music playback (pygame.mixer.music)
• Fade-out / fade-in transitions
• Hard cuts (for dramatic stings)
• Temporary overrides (dialogue / popup scenes)
• Interrupt tracks that resume previous music when finished
• Sticky behavior (music persists unless explicitly overridden)

Important constraints:
• pygame.mixer.music is single-channel → no true crossfade
• Fades are implemented as fade-out → delayed play
• Fail-soft: audio errors never crash the game

-------------------------------------------------------------------------------
SCENE-DRIVEN MUSIC DECLARATION

Scenes may declare music intent using simple attributes:

    music_key = "menu"          # registry key
    music_playlist = ["a", "b"] # optional pool (randomly chosen)
    music_loop = True
    music_hard_cut = False
    music_fade_out_ms = 700
    music_fade_in_ms = 700

If a scene declares NONE of these, it does NOT affect music.
Current music continues ("sticky" behavior).

Typical usage:
• Main menu declares menu music
• Dungeon scene declares dungeon playlist
• Options / save / character creation declare nothing (inherit)

-------------------------------------------------------------------------------
WINDOW SCENES & OVERRIDES (DIALOGUE, POPUPS)

Overlay scenes (DialoguePopupScene, urgent popups, etc.) may temporarily override
music while they are open.

Convention:
• A scene is considered a WINDOW scene if:
      scene.window_rect is NOT None

Window scenes may declare:
    music_override_key = "npc_theme"

While the window is open:
• Its override music plays
• Underlying base scene music is paused conceptually
When the window closes:
• SceneManager resyncs and base music resumes

IMPORTANT:
Fullscreen PanelScenes use window_rect = None and are BASE scenes,
not overlays.

-------------------------------------------------------------------------------
INTERRUPT MUSIC (EVENT STINGS)

AudioManager supports one-shot interrupt tracks that resume previous music when
finished (e.g. dramatic events, cutscenes).

API:
    audio.interrupt_then_resume(
        MusicRequest(key="event_theme", loop=False),
        resume_to=previous_request
    )

Used for:
• Story beats
• Boss reveals
• Non-looping narrative music

Interrupt tracks rely on pygame's MUSIC_END_EVENT to resume correctly.

-------------------------------------------------------------------------------
SCENE MANAGER INTEGRATION

SceneManager owns music synchronization via:

    sync_music_to_scene_stack()

Rules:
1) Topmost WINDOW scene with override wins
2) Otherwise, topmost BASE scene with music intent wins
3) Otherwise, do nothing (music persists)
4) If stack is empty, stop music

AudioManager is ticked once per frame:
    audio.update()

AudioManager consumes its own pygame events:
    audio.handle_pygame_event(event)

-------------------------------------------------------------------------------
WHY THIS DESIGN?

• Matches the scene stack model already used everywhere else
• Prevents audio ownership conflicts
• Makes dialogue and popups trivial
• Avoids reloading music on minor scene transitions
• Scales cleanly to biome music, combat stingers, and future systems

Key principle:
Scenes DECLARE intent.
SceneManager ARBITRATES.
AudioManager EXECUTES.

-------------------------------------------------------------------------------
ADDING NEW MUSIC

1) Add file to assets/music/
2) Register key in SceneManager.__init__:
       self.audio.register_music("key", "path.wav")
3) Declare music_key on the relevant scene

No other wiring required.

SECTION 8 — ENTITY, PROTOTYPES, & ONTOLOGY

Edgecaster uses a data-driven prototype system to define all entities in the world:
players, enemies, NPCs, items, terrain features, body parts, and abstract constructs.

Prototypes

• Prototypes are defined in YAML data files (e.g. entities.yaml, enemies.yaml, biology.yaml, anatomy.yaml).
• All prototype files are merged into a single master prototype pool at load time.
• Prototypes form a single inheritance tree rooted at the ur-entity.

Inheritance rules:
• A prototype may define parent: (ontological “is-a” inheritance).
• Any field defined on a parent is inherited by children unless overridden.
• Nested dictionaries are merged; lists override by default.
• Structural deletions may be expressed via explicit patch operations.

Resolution:
• All gameplay systems use resolved prototypes, not raw YAML entries.
• Prototype resolution is centralized in prototypes.py.

Entities (runtime instances)

• An Entity is a runtime instance created from a resolved prototype.
• Instances store only:
– per-instance state (position, hp, statuses, inventory, etc.)
– a reference to their originating prototype id (for save/load and introspection).

Entities are intentionally lightweight; structure lives in data.

Body schemas & subparts

• Prototypes may define a body schema describing attachable subparts as a graph.
• Body schemas are pure data:
– nodes reference prototype ids for parts (e.g. hand, head)
– edges describe attachment (“part-of”), not ontological inheritance
• Ontological parentage (parent:) and attachment parentage are distinct concepts.

Inheritance:
• Body schemas inherit down the prototype chain.
• Descendants may modify structure using body_patch operations
(add/remove/replace nodes, change attachment topology, adjust layout hints).

Fractal attention & instantiation

• Body schemas describe what could exist; they do not force instantiation.
• Subpart entities are instantiated lazily, only when attention requires it
(inventory view, targeted actions, damage resolution, etc.).
• This mirrors the game’s zoom/LoD philosophy: structure exists independently of observation.

Actor-ness & agency

• “Actor” is not an ontological category.
• Agency (participation in the energy/action queue) is granted via properties/tags
and handled by systems, not inheritance.

Key principle:

Everything is an entity; differences emerge from data, inheritance, and attention.

-------------------------------------------------------------------------------
Runtime tags vs YAML tags (important)

 For Actors built from `content/enemies.yaml`, the YAML `tags:` field is preserved under
  `actor.tags["tags"]` (it may be a dict or list). Do not assume those keys are flattened
  into `actor.tags`.
 For gameplay logic that needs YAML tags, either:
  - read `actor.tags["tags"]` defensively (see `Game._attack`'s `_has_class_tag`), or
  - resolve the prototype via `prototypes.resolve_proto(actor.proto_id)`.

-------------------------------------------------------------------------------
Action timing, cooldowns, and timed modifiers

 Canonical action definitions live in `edgecaster/systems/actions.py` (ActionDef registry).
 Player actions should execute via `Game.queue_actor_action` (handles confirmations, item
  charges, cooldown origins, and time advancement).
 AI actions are chosen by `edgecaster/systems/ai.py` and executed in `Game._monster_act`.
  AI must respect `Entity.cooldowns` + `ActionDef.cooldown_ticks` (cooldowns are ticked in
  `Game._cooldown_tick`).
 Timed combat/time modifiers live on runtime tags and tick down in `Game._cooldown_tick`:
  - `frozen_slow` / `frozen_slow_timer` (multiplicative slow)
  - `action_tick_offset` / `action_tick_offset_ticks` (additive tick offsets, clamped to
    keep non-instant actions at >= 1 tick; used by War Drummer haste)

-------------------------------------------------------------------------------
Data-driven enemy combat hooks

 Some on-hit / on-death behaviors are data-driven via YAML tags and handled centrally in
  `Game._attack` (e.g. `xp_drain`, `lifesteal_frac`, `currency_min/max`).

SECTION 9 - MAP SCALE & ZOOM PHILOSOPHY (NEW)

Key invariant:
• The dungeon, overworld, and world map are the SAME grid,
  viewed at different scales.

Zoom behavior:
• Zooming out does NOT switch scenes or renderers
• Local tiles fade out as global LoD tiles fade in
• Camera pan/zoom applies uniformly at all scales
• The player remains the spatial anchor unless explicitly reset

Performance rule:
• ASCII rendering remains active at all scales
• No forced transition to “beautiful but slow” modes

SECTION 10 - GAME SYSTEMS (edgecaster/systems/)

Game.py decomposition extracts cohesive subsystems into dedicated modules.
Game class remains the orchestrator; subsystems handle domain logic.

-------------------------------------------------------------------------------
Extracted Systems (in systems/):

params.py
• ParamManager class for stat-gated action parameters
• Manages param_defs (per-action parameter bounds) and param_state (current indices)
• Handles stat-based gating (e.g., "requires 3+ focus to unlock damage level 2")
• Interface: ParamManager.get_value(action, key), .adjust(action, key, delta)

legendaries.py
• Legendary creature generation and POI discovery
• Allocates unique lair POIs for procedurally-generated bosses
• Tracks rumored vs discovered POIs for world map visibility
• Interface: init_legendaries(game), add_poi_rumor(game, poi_id), discover_pois_for_level(game, level)

lorenz_aura.py
• Strange Attractor's butterfly storm game integration
• Contact damage to enemies overlapping the projected storm
• Zone transition handling (hard-snap storm to player)
• Uses lorenz.py for core math; this module is game-side orchestration
• Interface: advance_lorenz(game, level, delta), reset_on_zone_change(game, player), has_lorenz_aura(game)

action_runner.py
• Unified action execution for players and AI
• Handles cooldown gating, charge consumption (wands), confirmation prompts
• Calculates final delay with slow/haste modifiers
• Eliminates divergence between player (queue_actor_action) and AI (_monster_act) paths
• Interface: run_action(game, actor_id, action_name, ...), run_ai_action(game, actor_id, action_name, ...)

spawning.py
• Entity factories and spawn orchestration
• Template loading and caching for enemies (enemies.yaml) and entities (entities.yaml)
• Position finding for valid spawn locations
• Actor registration with AI scheduling
• Spawn functions: enemies, imps, echoes, berries, NPCs, mentor
• Interface: spawn_enemies(game, level, count), spawn_entity_from_template(game, template_id, pos), register_actor(game, level, actor)

inventory.py
• Container logic and item manipulation
• Inventory access and creation (get_inventory, get_player_inventory)
• Pick up and drop items (player_pick_up, drop_inventory_item)
• Move items between inventories (recursive container handling)
• Equipment tagging (equip/unequip slots)
• Eating/consuming items
• Interface: player_pick_up(game), drop_inventory_item(game, index), move_item_between_inventories(game, src, idx, dest), equip_item_to_slot(game, owner, item, slot)

pattern_ops.py
• Pattern projection and vertex queries (world-space conversion)
• Neighbor graph traversal (BFS for neighbor_set_depth)
• Pattern placement mode (begin_place_mode, try_place_terminus)
• Pattern reset and motion (push_pattern)
• Note: Complex tick-based actions (act_ignite, act_regrow, act_freeze) remain in game.py due to scheduler coupling
• Interface: projected_vertices(game), nearest_vertex(game, pos), neighbor_set_depth(game, seed, depth), reset_pattern(game), push_pattern(game, level, target, rotation)

scheduling.py
• Event scheduling with heapq priority queue
• Time advancement and event processing
• Periodic regen ticks (HP regeneration)
• Cooldown decay for entities, actors, and inventory items
• Coherence drain based on pattern vertices (pattern unraveling at zero)
• Frozen/slow effect decay, attack bonus decay, action tick offset decay
• Interface: schedule(game, level, delay, action), advance_time(game, level, delta), start_regen(game, level, actor_id, amount, interval), coherence_tick(game, level, delta), cooldown_tick(game, level, delta)

combat.py
• Attack resolution and damage calculation
• Hostility checks (via reputation system delegation)
• Death handling and cleanup (removing actors, awarding XP)
• Currency drops and prototype-driven item drops
• Lifesteal and XP drain mechanics
• Slaver pack chain-breaking on death
• Interface: is_hostile(game, attacker, target), attack(game, level, attacker, defender), kill_actor(game, level, actor, killer_id, killer_is_player)

zones.py
• Zone retrieval with lazy creation
• Pattern/coherence reset on zone entry
• Stair usage (up/down) with player movement
• Zone boundary transitions (edge wrapping)
• Fast travel to overworld zones
• Note: _make_zone creation logic remains in game.py due to heavy POI/mapgen coupling
• Interface: get_zone(game, coord, up_pos), get_zone_for_render(game, coord), use_stairs_down(game), use_stairs_up(game), transition_edge(game, actor, dx, dy), fast_travel_to_zone(game, zx, zy)

overmap.py
• Julia coordinate grid (tile_julia_grid) for fractal terrain generation
• Overmap parameter initialization from WorldMapScene visual entry
• Background world map rendering thread (with request queueing and staleness detection)
• Corruption level, hotspots, and anchors (rune anchor POI suppression zones)
• Zone-to-Julia coordinate mapping for local zone generation
• Key design: overmap is "intimately linked" with local map generation - local zones query the Julia grid to sample the fractal at correct coordinates
• Interface: build_tile_julia_grid(game), init_overmap_params_and_grid(game), init_rune_anchors(game), start_world_map_thread(game, reason, width, height, span, view, view_token, corruption_version), ensure_overmap_ready(game), jx_jy_slices_for_zone(game, coord), set_corruption_level(game, level), set_corruption_spline_weight(game, weight), add_corruption_hotspot(game, jx, jy, strength, sigma), add_corruption_anchor(game, jx, jy, sigma, strength, coord, spawn_pos), refresh_corruption_visuals(game)

Integration Pattern:

Game class retains thin wrappers that delegate to subsystems:
    def add_poi_rumor(self, poi_id, *, log=True):
        legendaries_system.add_poi_rumor(self, poi_id, log=log)

Subsystems accept (game, ...) as first parameter for access to shared state.
TYPE_CHECKING imports prevent circular dependencies.

Trade is implemented as a standard PanelScene popup with no renderer-side logic.

Key modules:

edgecaster/systems/trade.py
 Canonical trade rules (pricing, funds, restock scheduling)
 Supports staged proposals: UI builds a proposal, then commits atomically on Accept

edgecaster/scenes/merchant_scene.py
 Merchant UI (buy/sell lists + Accept/Cancel)
 Esc cancels (discard proposal) and exits; Accept commits and exits

Data-driven content:

edgecaster/content/merchants.yaml + edgecaster/content/merchants.py
 Merchant definitions (funds, restock interval, stock table, price multipliers)

Adding a merchant NPC:
 Prefer routing instantiation through the prototype/spawn pipeline (spawn_factory/enemy_factory)
 NPC metadata lives in edgecaster/content/npcs.py (NPC_DEFS)
 POI placement for persistent merchants should live in edgecaster/content/pois.yaml
