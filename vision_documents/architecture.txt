EDGECASTER ARCHITECTURE GUIDE
High-Level Overview and Refactor Roadmap
Updated: 2025-12-22
Status: Widget system stable; PanelScene foundation stable; map zoom refactor complete

This document orients new contributors to the current structure.
It must remain concise, accurate, and immediately useful.

===============================================================================
SECTION 1 — CORE RESPONSIBILITIES

SCENES (edgecaster/scenes/)
Own:

• Scene-local UI state and flow
• Input interpretation (via GameCommand / MenuInput)
• Scene transitions and stacking (SceneManager)
• Declaring visual effects by NAME
• Declaring which overlay widget layers are active

Do NOT:

• Perform low-level rendering
• Apply pygame transforms directly
• Implement simulation rules

Key scene modules:

manager.py  
– Scene stack + popup/window stack  
– Overlay widget layer service (e.g. "hud")

base.py  
– Scene base types  
– PanelScene (widget-driven foundation)  
– GeneralMenuScene (selection, confirm/cancel, scrolling)  
– MenuFrameWidget (standard banner/body/list/footer layout)  

dungeon.py  
– Primary gameplay scene  
– TargetMode flow + UI routing  
– Camera-relative map presentation (renderer-driven)

IMPORTANT: Avoid importing the scenes package root at module import time.

===============================================================================
SECTION 2 — RENDERING, CAMERA, & MAP ZOOM

RENDERERS (edgecaster/render/)
Pure view layer.

ascii.py:
• ASCII rendering for dungeon, overworld, entities, overlays
• Draws terrain at multiple levels of detail (LoD)
• Applies VisualProfiles and VisualEffects at draw time
• Delegates all camera math and LoD policy elsewhere

Renderers NEVER:
• Read input events
• Interpret GameCommands
• Store gameplay or UI state

CAMERA (edgecaster/camera.py)

camera.py:
• Owns the canonical tile-space camera
• World position + zoom live here
• Handles:
  – zoom stepping and damping
  – cursor-anchored zoom
  – pan in pixel or tile space
  – world ↔ screen coordinate transforms
• Renderer-agnostic (can drive ASCII, tiles, sprites)

This enforces the invariant:
→ There is ONE camera for all zoom levels.

===============================================================================
SECTION 3 — MULTI-SCALE MAP RENDERING (LoD)

OVERMAP LOD (edgecaster/render/overmap_lod.py)

overmap_lod.py:
• Responsible for zoomed-out terrain aggregation
• Renders a snapped, rigid grid of “LoD cells”
• Each LoD cell summarizes many local tiles:
  – glyph sampling / majority / weighted biome logic
• Handles fade/blend thresholds between:
  – local tiles
  – global (condensed) tiles
• Owns caching keyed by:
  – world region
  – zoom level
  – sampling parameters

Key property:
• LoD tiles do NOT “swim” under camera motion.
  They remain locked to world tile boundaries.

Optional acceleration:
• Uses overmap_accel (numpy) when available
• Scalar fallback remains deterministic

===============================================================================
SECTION 4 — MAP GENERATION & BIOMES

MAP GENERATION (edgecaster/mapgen.py)

mapgen.py:
• Generates local overworld zones (depth 0)
• Uses the same Julia-plane mapping as the overmap
• Converts sampled fields → terrain glyphs/colors
• Supports fast numpy grid paths

BIOMES (edgecaster/biome.py)

biome.py:
• Centralizes biome definitions
• Maps sampled fields → biome indices
• Provides:
  – glyph choices
  – base color/tint
  – biome-level semantics
• Shared by:
  – local zone generation
  – overmap / LoD glyph sampling

This prevents drift between “what the world looks like”
and “what local terrain becomes.”

SECTION 5 — INPUT

INPUT (edgecaster/scenes/game_input.py)

Single conversion point:
Pygame Event → GameCommand

Scenes interpret GameCommands.
Renderers and camera are input-agnostic.

SECTION 7 — PANELSCENE & WIDGET SYSTEM

Widget foundation (edgecaster/ui/widgets.py):

• WidgetContext(surface, game, scene, renderer)
• Widget base class (layout, draw, handle_event, update)
• Layout containers (VBox/HBox)
• Interactive widgets (Label, Button, List, etc.)
• Wrapped-text widgets (pixel-based, no ellipses)
• Scaled label widgets for title hierarchy

Ownership model:
• Scenes own widget trees
• Input routed to widgets first
• Renderer remains draw-only

PanelScene (edgecaster/scenes/base.py):

• Owns logical panel surface + rect (fullscreen or popup)
• Owns root widget tree
• Routes input to widgets FIRST
• Applies VisualProfiles / VisualEffects consistently
• Converts mouse events to panel-local coordinates

GeneralMenuScene:

Built on PanelScene.
Provides:
• Selection model
• Confirm/cancel behavior
• Scrolling
• Keyboard + mouse arbitration

MenuFrameWidget:
Standard layout:
• Title/banner at top
• Optional body text
• Scrollable list
• Optional footer pinned bottom

SECTION 8 — ENTITY, PROTOTYPES, & ONTOLOGY

Edgecaster uses a data-driven prototype system to define all entities in the world:
players, enemies, NPCs, items, terrain features, body parts, and abstract constructs.

Prototypes

• Prototypes are defined in YAML data files (e.g. entities.yaml, enemies.yaml, biology.yaml, anatomy.yaml).
• All prototype files are merged into a single master prototype pool at load time.
• Prototypes form a single inheritance tree rooted at the ur-entity.

Inheritance rules:
• A prototype may define parent: (ontological “is-a” inheritance).
• Any field defined on a parent is inherited by children unless overridden.
• Nested dictionaries are merged; lists override by default.
• Structural deletions may be expressed via explicit patch operations.

Resolution:
• All gameplay systems use resolved prototypes, not raw YAML entries.
• Prototype resolution is centralized in prototypes.py.

Entities (runtime instances)

• An Entity is a runtime instance created from a resolved prototype.
• Instances store only:
– per-instance state (position, hp, statuses, inventory, etc.)
– a reference to their originating prototype id (for save/load and introspection).

Entities are intentionally lightweight; structure lives in data.

Body schemas & subparts

• Prototypes may define a body schema describing attachable subparts as a graph.
• Body schemas are pure data:
– nodes reference prototype ids for parts (e.g. hand, head)
– edges describe attachment (“part-of”), not ontological inheritance
• Ontological parentage (parent:) and attachment parentage are distinct concepts.

Inheritance:
• Body schemas inherit down the prototype chain.
• Descendants may modify structure using body_patch operations
(add/remove/replace nodes, change attachment topology, adjust layout hints).

Fractal attention & instantiation

• Body schemas describe what could exist; they do not force instantiation.
• Subpart entities are instantiated lazily, only when attention requires it
(inventory view, targeted actions, damage resolution, etc.).
• This mirrors the game’s zoom/LoD philosophy: structure exists independently of observation.

Actor-ness & agency

• “Actor” is not an ontological category.
• Agency (participation in the energy/action queue) is granted via properties/tags
and handled by systems, not inheritance.

Key principle:

Everything is an entity; differences emerge from data, inheritance, and attention.

SECTION 9 — MAP SCALE & ZOOM PHILOSOPHY (NEW)

Key invariant:
• The dungeon, overworld, and world map are the SAME grid,
  viewed at different scales.

Zoom behavior:
• Zooming out does NOT switch scenes or renderers
• Local tiles fade out as global LoD tiles fade in
• Camera pan/zoom applies uniformly at all scales
• The player remains the spatial anchor unless explicitly reset

Performance rule:
• ASCII rendering remains active at all scales
• No forced transition to “beautiful but slow” modes
