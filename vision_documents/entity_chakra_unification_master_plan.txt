## Entity + Chakra Unification Master Plan
Updated: 2026-04-23
Status: v1.65 (refined the pragmatic refactor endgame around unified authority and maintainability)

This is the execution plan for:

1. Everything with persistent gameplay identity or compositional participation is an entity.
2. "Chakra" is a role/query word for an entity within a larger hierarchy, not a second ontology.
3. The canonical organization is a strict containment tree plus expandable typed relation edges.
4. Geometry is first-class, stored canonically in absolute world space, and queryable through one shared interface.
5. Rules are scale-invariant by default.

This plan is intentionally implementation-first and absorbs the still-relevant
work that survived the earlier POI/entity unification plan.

-------------------------------------------------------------------------------

## Core Design Principles

1. Authority before caches
   - `entity_graph`, runtime entity records, and authoritative
     component/channel payloads are the real gameplay truth.
   - Side stores such as inventory lists, attention indexes, world indexes,
     scene collections, and similar mirrors may exist only as caches,
     indexes, or projections.
   - Every cache should declare its allowed freshness class:
     `event-consistent`, `tick-stale`, or `query-consistent`.

2. Query surfaces over storage leakage
   - Runtime projection helpers and scene view-model/query helpers are the same
     boundary problem at two different altitudes.
   - Simulation and UI should ask stable query surfaces for the payload they
     need instead of reaching through to graph internals, reducer caches, or
     legacy schema walkers.

3. Structural state vs streaming state
   - Structural state changes topology, ownership, unlocks, activations,
     layouts, or other facts that should dirty graph/reducer caches.
   - Streaming state changes frequently by design (charge, resonance, timers,
     gauges, and similar live values) and should usually stay on live
     component/query paths without forcing subtree invalidation unless a rule
     explicitly promotes it into structure.

4. Runtime truth vs UI session state
   - Runtime truth lives in entities, components, graph metadata, and reducer
     outputs derived from them.
   - UI/session objects are initialized from snapshots, mutated locally for
     preview/undo/drag, and committed back through explicit write operations.
   - No continuous sync loop should be required for edit-session state.

5. Deterministic layout resolvers
   - Authored sources resolve into deterministic child specs, optional
     realization, and shared geometry/query surfaces.
   - `entity_body.py` is the first concrete layout resolver; future building,
     neighborhood, city, faction, and organization layouts should follow the
     same pattern.

6. Containment is structure; relations are interaction
   - Parent/socket links encode the one strict containment tree.
   - Typed relation edges encode non-parental interaction such as resonance,
     conduits, favor, support, alignment, or similar cross-links.
   - High-churn overlap/contact should usually be represented by geometry
     queries or ephemeral contact indexes, not by persistent graph edges that
     would structurally dirty the graph every tick.

7. Topology convergence is the long-term target
   - The long-term destination is for authoritative topology to live in
     `EntityGraph` containment plus typed relations, not in a parallel chakra
     subgraph hidden inside components.
   - During migration, `ChakraComponent` may still carry adapter/cache/query
     payloads where that shortens the path to a clean cutover.
   - Universal channels stay minimal (`hp`, `mass` baseline); entity-specific
     channels remain extensible instead of being frozen prematurely into one
     closed struct.

8. Prefer maintainable boundaries over purity churn
   - We do not need to force every remaining helper or container to disappear
     if doing so would mostly reshuffle code without clarifying authority.
   - A thin wrapper may survive if it becomes the one clearly blessed surface
     instead of a hidden second authority.
   - The refactor is successful when new work naturally uses the unified
     surfaces, not when every old noun has been deleted for its own sake.

## Pragmatic Endgame (2026-04-23)

The foundational unification work is now largely in place.  The remaining plan
should optimize for clear authority and easy maintenance, not abstract purity.

What is already unified enough to build on:

1. Chakra/body runtime authority:
   - `ChakraComponent`, shared projections, entity-body specs, and reducer
     helpers are now strong enough that new gameplay should build on them
     directly instead of reviving `ChakraState` or raw schema traversal.

2. Inventory/equipment containment:
   - Graph-authoritative sockets are the real source of truth. That track is
     complete enough that follow-on work should assume it is stable.

3. Spatial read surface:
   - `SpatialIndex` is now the primary shared spatial query layer for staged,
     proxy, collapsed, and loaded runtime entities.

4. Transient runtime effects:
   - The original vine/projectile/effect migration cluster is complete enough
     that new runtime effect work should spawn/query entities instead of adding
     new `LevelState` sidecars.

Remaining work that is still architecturally worth doing:

1. Finish the single spatial/query story.
   - Keep `SpatialIndex` as the only required spatial read surface.
   - `POIRegistry` spatial methods are now compatibility wrappers over
     `SpatialIndex` when attached; the remaining work is mainly about
     deciding whether `AttentionCellStore` should disappear entirely and how
     far the registry itself should shrink beyond semantic/content-state duty.

2. Finish lineage demotion.
   - `entity_id` is already the runtime persistence authority.
   - Snapshot writes no longer route through `lineage_id`, and snapshot apply
     no longer reinjects lineage-derived identity into runtime tags.
   - The shared snapshot bridge and resolver lifecycle no longer thread
     `lineage_id` through restore/suppression lookups; those paths now read
     persisted state by `entity_id` only.
   - The remaining job is to confine `lineage_id` to provenance,
     deterministic resolver history, and the few explicit read-compat shims
     that still remain rather than letting it quietly participate in identity
     or suppression truth.

3. Promote only high-value sidecars.
   - Promote runtime state into entities when shared geometry, lifecycle,
     inspection, persistence, or rendering clearly benefits.
   - Do not promote pure local/session/UI state just for symmetry.

4. Keep new gameplay on shared query surfaces.
   - New systems should prefer `entity_ops`, `entity_geometry`,
     `entity_lifecycle`, `SpatialIndex`, and reducer/projection helpers over
     store-specific queries or hand-rolled compatibility ladders.

Deliberate deferrals unless a concrete feature requires them:

- deleting `LevelState.actors` / `LevelState.entities` purely for ontology cleanup
- flattening `ChakraComponent` into a closed scalar-only struct
- deleting thin wrappers that already serve as the one clear surface
- moving every macro system (`blade_states`, gods, factions, sieges) into graph
  relations before gameplay pressure exists
- retiring `poi_worldgen.py` before the resolver/realization path offers a
  simpler replacement

Practical success condition:

- New features can be built without reopening the old split pipelines.
- Remaining bridges are few, local, documented, and non-authoritative.
- A subsystem is "done enough" when its authority/query story is clear, even if
  a thin adapter still exists around the edges.

## Current Snapshot (2026-04-23)

Implemented and stable:

1. Identity substrate:
   - `Entity` has Phase-1 fields (`entity_id`, `semantic_id`, `proto_id`,
     `lod_band`, `parent_entity_id`, `socket_id`, `chakra_component`).
   - Deterministic runtime IDs from seed + recipe + location are in use.

2. Persistence bridge:
   - `game.entity_state` exists and receives lifecycle writes.
   - Runtime removal/death/suppression now use `entity_id` only.
   - Legacy lineage write/read bridge methods were deleted from runtime codepaths.
   - Object/entity persistence writes now target the resolved `entity_id` key
     only. Legacy lineage data remains read-compat fallback rather than a peer
     write target.
   - Read compatibility now treats entity-keyed records as lifecycle- and
     ownership-authoritative; lineage may backfill old detail fields, but it
     no longer overrides suppression truth once an entity record exists.
   - Deterministic resolver/aggregate children now begin separating `eid` from
     `lineage_id` instead of treating lineage paths as runtime entity identity.
   - Unique world-root aggregates now keep historical root `eid` values for
     compatibility while using a distinct lineage namespace, so even parentless
     macro entities no longer collapse ancestry and identity into one string.
   - Attention realization no longer fabricates lineage from `eid` when a spawn
     intent omitted provenance; absence now stays absent instead of becoming a
     fake identity-shaped lineage.
   - Door state mutations now write immediate entity-state deltas in the same
     patch shape used by attention rehydration (`last_known_tags`,
     `last_known_glyph`, `last_known_blocks_movement`) instead of relying only
     on a later snapshot pass to preserve open/closed state.
   - Spawn and attention-stage paths initialize lifecycle flags in `entity_state`.

3. Footprint substrate:
   - Canonical footprint helpers exist and core occupancy/blocking checks are
     footprint-aware in spawn/AI/combat paths.

4. Inventory bridge:
   - Pickup/drop/transfer attach/detach parent/socket metadata.
   - Shared graph ops now exist for attach/detach/reparent operations.
   - Shared graph-op split now exists (`split_stack_entity`) with deterministic
     split identity + provenance tags.
   - Inventory/trade split callsites now use shared graph-op split directly.
   - Trade item moves (single + proposal flow) now route through shared
     graph transfer operations.
   - Inventory queries are now graph-authoritative; `game.inventories` has
     been deleted as a parallel containment store.
   - Equipment slots are modeled as socket-typed graph containment edges:
     inventory items live on `socket_id="inventory"` and equipped items live
     on their slot socket.

5. Chakra substrate kickoff:
   - Typed chakra dataclasses now exist:
     `ChakraNode`, `ChakraEdge`, `ChakraComponent`.
   - These are currently a migration surface for the unified hierarchical
     entity model, not a permanent second ontology.
   - Spawn factory now coerces YAML chakra payloads to typed components and
     guarantees a default `{entity_id}:core` node.
   - Legacy runtime bridges (`ensure_actor_chakra_state`, `sync_actor_chakra_state`)
     have been deleted.
   - `ChakraViewState`, `effective_chakra_view`, and `build_chakra_generator_seed_for_actor`
     are now the preferred paths for chakra queries and generation.
   - `body_view_queries.py` provides the shared scene query surface.
   - Actor-scoped chakra mutation wrappers now exist:
     `unlock_actor_chakra(...)`, `toggle_actor_chakra(...)`.
   - Monk unlock flow, Chakra Sage dialogue unlock flow, and Chakra Scene toggle
     interactions now route through wrapper mutations.
   - Spawn-time actor `ChakraState` bootstrap has been removed.
   - Chakra mutation wrappers now mark the entity graph dirty when a `game`
     context is available, so reducer cache invalidation follows real runtime
     writes instead of test-only helper calls.

6. Test posture:
   - Migration-focused suites are green (inventory, spawning, POI cutover,
     attention suppression, combat/action runner, rune siege, footprints,
     chakra component bootstrap, graph ops).

7. Phase 2 lifecycle/query substrate:
   - `EntityGraphStore` now tracks lifecycle/query metadata directly on nodes:
     `lod_state`, `layout_id`, and `rule_id`.
   - `edgecaster/systems/entity_snapshots.py` is now the shared owner of
     deterministic-child snapshot persistence/apply logic.
   - `edgecaster/systems/entity_lifecycle.py` now owns resolver-backed
     expand/collapse v0 for attention-managed descendants.

     query envelope plus `query_normalized_pattern(...)`.
   - Chakra seed generation now prefers shared component geometry when an actor

     body-schema path.
   - Runtime effective chakra reads (`effective_unlocked_nodes`,
     `effective_active_nodes`) now rebuild from the actor's

   - `pattern_runtime.act_chakra(...)` now stays on the entity/component path

   - `scenes/chakra_scene.py` now passes the live `game` context into

Not yet complete:

1. Unified graph storage is not authoritative yet.
   - Parallel stores still exist (`LevelState.actors/entities`, `attn_store`,
     `world_entity_index`, `poi_registry`).
   - Plan clarification: `entity_graph`, runtime entities, and component/channel
     payloads are the intended authorities. The listed side stores should
     converge toward caches/indexes/projections rather than remaining peer
     truth stores.
   - Freshness classes for those side stores are not yet consistently declared,
     so "cache" still remains too vague in some subsystems.
2. Chakra substrate integration is not complete.
   - Structural-vs-streaming distinctions are not yet encoded consistently
     enough; some high-frequency values still travel through paths that were
     originally designed for structural invalidation.
   - The deleted `ChakraState` facade no longer blocks runtime work, but
     legacy raw `body_schema` fallback paths still need to be isolated and
     trimmed before the chakra/body read path is fully unified.
   - The docs now lock in that every chakra is an entity; implementation still
     has to catch up to that simplification.
   - Long-term target is to dissolve remaining authoritative topology out of
     `ChakraComponent` so containment + typed relations carry structure while
     components shrink toward channel payloads, adapters, and query surfaces.
   - `chakra_layouts.yaml` + `chakra_rules.yaml` now exist, and reducer-backed
     charge evaluation has entered runtime, but most gameplay still reads
     compatibility adapters instead of shared geometry/rule queries.
   - Migration should continue by replacing facade reads with thin
     projection/query helpers wherever possible, not by forcing every caller to
     consume raw graph internals directly.
3. POI realization facade deleted; single pathway now lives in `poi_worldgen.py`.
   - `poi_spawning.py` deleted (2026-04-13); `test_poi_spawning_cutover.py`
     migrated to import `poi_worldgen` directly.
   - `poi_worldgen.py` itself still carries a `[LEGACY_DELETE]` tag pending
     full resolver/entity-graph realization pipeline convergence.
4. Split-stack, container, and equipment flows need post-cutover cleanup.
   - Shared graph-op split and graph-authoritative inventory containment are
     in place. Remaining work is to audit tests, stale docs, and leftover
     compatibility fallbacks now that list-backed inventory authority is gone.
5. Read compatibility still merges legacy lineage state where present.
   - This is intentional for migration safety, but the long-term goal is for

6. Some attention/resolver paths still carry lineage-heavy assumptions.

## Completion Roadmap For The Remaining Large Architectural Pieces (2026-04-21)

This section answers a narrower execution question than the phase descriptions
above: what are the biggest remaining architectural cuts, and in what order
should they be completed so we do not delete one compatibility layer only to
quietly rebuild the same split somewhere else.

The remaining work clusters into two large programs:

1. Read-path consolidation
   - Finish moving gameplay, scenes, and tests onto shared query/projection
     surfaces.
   - Delete `ChakraState`, raw body-schema traversal, and scene-local fallback
     ladders once they are no longer needed.

2. Authority-path consolidation
   - Finish turning graph/runtime entities into the only real authority and
     demote the remaining side stores to explicit caches or delete them.
   - This includes the loaded-zone actor/entity dicts, attention staging
     caches, macro-world indexes, POI registries, inventory list caches, and
     ad hoc LevelState runtime effect dicts.

Recommended dependency order:

1. Close the remaining chakra/body read-model bridges.
2. Introduce one shared runtime entity/realization query surface.
3. Cut containment/inventory/equipment fully over to graph authority.
4. Collapse attention, world-index, and POI lookup onto one realization/index
   model.
5. Promote transient runtime side stores into ordinary entities/components.
6. Finish persistence cleanup and final legacy deletion.
7. Expand Phase 3 rule data and geometry-aware reducers once the runtime/query
   surfaces are stable enough to stop moving underneath them.

### Track A - Delete ChakraState And Raw Body-Schema Runtime Reads (COMPLETE)

Why this is first:
- The nominal `ChakraState` class is now gone, which removes the easiest path
  for new code to slip back into the actor-only worldview.
- The remaining Track A work is to keep shrinking the raw body-schema fallback
  paths until they are clearly legacy-only instead of a normal runtime option.

Primary targets:
- `edgecaster/systems/chakras.py`
- `edgecaster/systems/chakra_items.py`
- `edgecaster/scenes/chakra_scene.py`
- `edgecaster/scenes/inventory_scene.py`
- any tests or docs that still assume a nominal actor-side chakra facade

Execution strategy:
1. Keep `build_chakra_generator_seed(...)` and related readers accepting thin,
   dict-like read snapshots rather than a typed facade.
2. Move the last body-schema recursive readers behind explicit legacy fallback
   helpers so runtime callers default to `entity_body.py`,
   `body_view_queries.py`, and `entity_geometry.py`.
3. Delete or rewrite any stale tests/docs that still talk as if
   `ChakraState(...)` were a live production surface.

Done looks like:
✓ No runtime code constructs or requires a nominal actor-side chakra facade.
✓ Remaining body-schema traversal is either gone or clearly isolated as
  pre-runtime/editor-only fallback.
✓ Chakra Scene and Inventory Scene read shared query/view-model helpers rather
  than open-coding their own ladders.

### Track B - Add One Shared Runtime Entity Query Surface Before Deleting Zone Stores (COMPLETE)

Why this is second:
- `LevelState.actors` / `LevelState.entities` are still referenced across AI,
  actions, combat, scheduling, scenes, and inspection. Deleting them directly
  would be noisy and brittle.
- The safer path is to hide them behind one shared read surface first, then
  change the backing store later.

Primary targets:
- `edgecaster/game.py`
- `edgecaster/systems/session.py`
- `edgecaster/systems/entity_lifecycle.py`
- `edgecaster/systems/entity_ops.py`
- `edgecaster/systems/render_query.py`
- all actor/entity iteration callsites

Execution strategy:
1. Introduce or expand a small shared runtime-entity query layer for:
   - get entity by id
   - get actor by id
   - iterate realized actors/entities for a level
   - iterate realized occupants in a rect/zone/view
2. Migrate high-fanout consumers (`actions.py`, `combat_actions.py`,
   `scheduling.py`, `ai.py`, scenes) onto that query layer.
3. Only after callsites converge, replace the direct dict ownership model with
   a more explicit realization registry or graph-backed view.

Done looks like:
✓ Most code no longer reaches directly into `level.actors` / `level.entities`.
✓ Loaded-zone membership becomes a declared cache/projection, not an ambient
  hidden authority.

### Track C - Finish Graph-Authoritative Inventory And Equipment (COMPLETE)

Why this is third:
- Inventory was the cleanest player-facing containment loop to finish first.
  Completing it validates the graph-authority contract before the harder
  world-scale cuts.

Primary targets:
- `edgecaster/systems/inventory.py`
- `edgecaster/systems/equipment.py`
- `edgecaster/systems/trade.py`
- `edgecaster/systems/entity_graph_ops.py`
- stale inventory compatibility fallbacks, tests, and docs

Execution strategy:
1. `get_inventory(...)` now builds from graph containment instead of falling
   back to an owner list.
2. Equipment slots are represented as socket-typed containment edges.
3. Trade, split-stack, startup-item, and bag/container flows should continue to
   route through graph attach/detach/reparent operations.
4. `game.inventories` has been deleted as a parallel containment store.
   Remaining work is cleanup and parity hardening, not authority design.

Done looks like:
- Inventory and equipment are containment queries, not side dictionaries.
- List caches are rebuildable views only.

### Track D - Unify Attention, World Index, And POI Lookup Into One Realization/Index Model (ADVANCED)

Why this is fourth:
- `attn_store`, `world_entity_index`, and `poi_registry` currently solve
  related lookup problems with different ontologies.
- This is the biggest remaining source of "cache that sometimes behaves like
  truth" outside the loaded-zone dicts.

Primary targets:
- `edgecaster/systems/attention.py`
- `edgecaster/systems/spatial_index.py`
- `edgecaster/systems/world_entity_index.py`
- `edgecaster/systems/poi_registry.py`
- `edgecaster/systems/poi_worldgen.py`
- `edgecaster/systems/aggregate_resolution.py`
- `edgecaster/systems/site_placement.py`

Execution strategy:
1. Separate three concerns explicitly:
   - containment/identity authority -> `entity_graph`
   - realization lifecycle -> `entity_lifecycle`
   - spatial/semantic lookup indexes -> one declared index layer
2. Add shared query helpers for:
   - query by semantic id / kind
   - query by ABS rect
   - query realized vs collapsed status
3. Port world-map, overmap, inspection, and attention consumers to those
   shared queries before deleting store-specific APIs.
4. Collapse `poi_registry` toward semantic-id queries on ordinary entities.
5. Collapse `world_entity_index` and `AttentionCellStore` toward one spatial
   index model keyed by `entity_id` plus realization state.

Current status:
- Slice D.1 established `SpatialIndex` in `edgecaster/systems/spatial_index.py`
  as the intended shared hierarchical ABS-rect index. It tracks absolute
  geometry, realization state, semantic ID, and kind, and is designed to subsume
  `AttentionCellStore`, `WorldEntityIndex`, and `POIRegistry` once those callers
  are migrated.
- Slice D.2/D.3 started wiring the index into runtime: `Game` now owns
  `spatial_index`, `AttentionCellStore` mirrors staged entities into it,
  `WorldEntityIndex` mirrors proxy entities into it, and distant-look
  inspection uses the shared query surface before falling back to legacy stores.
- Slice D.4 moved additional low-risk readers onto that shared query surface:
  dungeon look targeting and spatial music tagged-world-entity probes now read
  `SpatialIndex` first, with legacy store-specific fallbacks retained during
  migration.
- As of 2026-04-23, `_runtime_entity_registry` and `WorldEntityIndex` have
  already been removed from the live runtime path.
- Also as of 2026-04-23, `attention.py` / `entity_lifecycle.py` staged-entity
  readers no longer depend on raw `attn_store.entities` dict access; they now
  use an explicit staged-query surface so `AttentionCellStore` behaves more
  like a narrow staging adapter than a second ad hoc object store.
- Aggregate/detail realization in `attention.py` is also being narrowed: the
  cluster-child path now goes through explicit stage/mirror/promote/drop
  helpers instead of treating the store + level dicts as one intertwined local
  implementation detail.
- The remaining D-track question is now narrower and more pragmatic: either
  delete `AttentionCellStore` / narrow `POIRegistry` further, or explicitly
  bless them as thin write/service helpers with no competing query semantics.

Done looks like:
- POIs, macro entities, staged attention entities, and loaded-zone entities are
  different realization states of one ontology.
- Lookup APIs stop caring which legacy store happened to answer the question.

### Recommended Near-Term Slice Order

If we want the next several meaningful steps in practical order, the
recommendation is now:

1. Finish the spatial endgame decision:
   - either delete `AttentionCellStore` as an exposed concept, or bless it as a
     narrow staging helper that writes only into `SpatialIndex` and never acts
     like an alternate query authority.
   - This is partly done now: staged-object readers no longer reach through the
     raw `attn_store.entities` dict and instead use the store's helper surface.
   - Aggregate child promotion/despawn now also flows through explicit helper
     boundaries, which makes the remaining AttentionCellStore deletion surface
     much smaller.
2. Narrow `POIRegistry` to semantic/content-state responsibilities only:
   - spatial reads should stay on `SpatialIndex`; registry logic should exist
     only where content-state persistence still truly needs it.
   - This is partly done now: when a shared index is attached, the registry's
     compatibility spatial reads already delegate to `SpatialIndex`.
3. Finish lineage demotion:
   - clean up remaining lineage-aware state fallbacks in attention/lifecycle
     so `lineage_id` is clearly provenance, not shadow identity.
   - As of 2026-04-23, the shared snapshot bridge and resolver lifecycle have
     already dropped lineage-threaded restore/suppression lookups; the
     remaining work is in higher-level compat surfaces, not the core
     collapse/rehydrate path.
4. Promote only the next high-value transient sidecars:
   - candidates such as `seal_trial`, `rune_anchor_siege`, or similar runtime
     event families should move only if entity treatment buys us shared
     geometry/lifecycle/persistence value.
5. Re-evaluate the loaded-zone containers only after the above:
   - do not force deletion of `LevelState.actors` / `LevelState.entities`
     unless a concrete single-container design clearly improves ownership,
     testing, and maintenance.

This order keeps us deleting the smallest but most architecture-distorting
compatibility layers first, then attacking the bigger shared-runtime surfaces
with fewer moving parts still attached.

identity/provenance and door-persistence work.

   - `EntityGraphNode` now carries `lod_state`, `layout_id`, and `rule_id`.
   - Registration helpers and major spawn/world-entry paths now populate those
     fields explicitly instead of hiding them only in tags.

   - Snapshot/apply helpers moved into `edgecaster/systems/entity_snapshots.py`.
   - `attention.py` now delegates snapshot persistence/apply there.
   - `entity_ops.toggle_door(...)` now uses the shared persistence helper.

   - `edgecaster/systems/entity_lifecycle.py` now exposes
     `expand_entity(...)` and `collapse_entity(...)`.
   - Scope is resolver-backed deterministic parents only, with idempotent
     direct-child realization and snapshot writeback on collapse.

   - `edgecaster/systems/entity_geometry.py` now returns the shared geometry
     envelope (`root_entity_id`, `realization_state`, `precision`, `nodes`,
     `edges`, `derived`, `warnings`).
   - `query_normalized_pattern(...)` now reconstructs a seed-pattern helper
     from `ChakraComponent` node/edge data when enough geometry exists.

   - `AttentionCellStore` now stages/querys by footprint-aware hierarchical
     rect cells instead of one ABS anchor bin.

     expand/collapse resolve parents based on warm-window + depth policy.

   - `entity_body.py` now produces deterministic layered body-node specs from
     resolved actor body schemas.
   - `entity_lifecycle.expand_entity(...)` can now realize body children under

## Phase 1 Contract Lock Outputs

Phase 1 is a documentation/contract pass intended to remove ambiguity before
the deeper code refactor begins.

This phase locks the core contracts:

1. Shared geometry query API
   - One raw query surface plus higher-level helper queries.
   - Explicit realization policy (`forbid`, `allow`, `require`).
   - Explicit precision reporting (`exact` vs `approximate`).
   - Canonical world-position semantics must support sub-tile float precision,
     not only integer tile anchors.
   - Query results must report realization/precision status explicitly and
     surface warnings such as `collapsed_subtree` or
     `exact_geometry_unavailable` instead of fabricating exactness.

2. Persistence patch envelope
   - One `entity_id`-keyed patch shape for state, geometry, and relation diffs.
   - `chakra_patch` remains the migration name, but semantically means
     composition/geometry diffs.

3. Containment vs typed relation semantics
   - Containment is the one true parent/child hierarchy.
   - Typed relations add interaction without creating parentage.
   - High-churn overlap/contact should usually be represented by geometry
     queries or ephemeral contact indexes, not authoritative graph edges.

4. `chakra_component` migration meaning
   - It may remain a cache/adapter.
   - It must not become the long-term authority for identity, parentage, or
     bespoke bypass semantics.
   - Long-term target: dissolve remaining authoritative topology out of
     `chakra_component` so `EntityGraph` containment + typed relations carry
     structure.
   - Do not prematurely freeze a closed `ChakraChannels` schema beyond the
     universal baseline; channels should stay extensible while the design is
     still expanding.

5. Runtime projection/query layer
   - Most gameplay and scene code should read structured projection/query
     payloads, not raw graph internals and not revived actor-scoped facade
     objects.
   - Projection helpers may be consumer-shaped as long as their data derives
     from authoritative entities, components, graph state, or reducer outputs.
   - Runtime projection helpers and scene view-model/query helpers are both
     part of this same stable boundary.

6. Runtime state vs UI session state
   - Runtime authoritative state must live in entities, components, graph
     metadata, or reducer outputs derived from them.
   - Scenes may keep transient edit-session objects for preview, undo, drag,
     or local editing, but those objects are not runtime truth and should be
     named/documented accordingly.
   - Edit-session objects initialize from snapshots, mutate locally, and write
     back through explicit commit operations rather than continuous sync.

7. Deterministic layout resolver contract
   - `entity_body.py` is the first concrete resolver proving the pattern.
   - Future building, neighborhood, city, faction, organization, and similar
     layout systems should expose the same authored-layout -> deterministic
     child-spec -> realization/query pipeline.

8. Authority vs cache contract
   - `entity_graph`, runtime entities, and authoritative component/channel
     state define truth.
   - Side stores, indexes, and projections may lag only according to their
     declared freshness class and must never accept hidden peer-authority
     writes.

9. Structural vs streaming state
   - Structural writes dirty graph/reducer caches because they change topology,
     ownership, activations, unlocks, or other persistent relations.
   - Streaming values stay on live component/query paths by default and do not
     imply subtree invalidation unless content rules explicitly say so.

10. Cache freshness classes
   - `event-consistent`: updates when the underlying event occurs.
   - `tick-stale`: may lag until the next scheduled tick.
   - `query-consistent`: may rebuild/revalidate on read.
   - "Rebuildable" is not enough; callers need to know when lag is allowed.

11. Long-term topology convergence
   - The finished architecture should not keep two peer structural ontologies.
   - Containment parent/socket links encode hierarchy; typed relation edges
     encode interaction in addition to containment, not as a replacement for
     it.
   - Migration helpers may temporarily keep node/edge mirrors inside
     `ChakraComponent`, but those mirrors should shrink over time rather than
     becoming permanent structural authority.

Execution priority (next refactor batches):

1. Query-surface cutover:
   - Migrate remaining runtime/scene `effective_chakra_state(...)` consumers to

## Decisions Locked In

1. Identity and persistence:
   - `entity_id` is immutable and is the primary persistence key.
   - `semantic_id` remains for quest and narrative meaning.
   - Multiple entities may share a `semantic_id` when they participate in the
     same gameplay concept.
   - `lineage_path` is contextual and may change when graph links change.

2. Spatial truth:
   - Canonical geometry is stored in absolute world space.
   - Parent-relative or local coordinate systems may be derived when useful,
     but they are adapters, not the source of truth.
   - Geometry formed by entity positions and links is canonical gameplay
     data, not renderer garnish.
   - Rune interactions, fractal growth, and future magic systems may query this
     geometry directly.
   - For now, assume all entities participate in this geometry/query surface.

3. Graph model:
   - One strict containment tree (single containment parent).
   - Additional typed graph edges allowed (`owns`, `influences`, `linked_to`, etc.).
   - Every chakra is an entity. "Chakra" describes an entity's role within a
     larger composition.
   - Current `ChakraComponent` records are a migration/cache structure, not a
     separate ontology.
   - "Owning a forest" means legal/control ownership edge, not inventory containment.

4. Query surface:
   - The shared geometry API must support raw positions/edges and richer derived
     primitives when useful.
   - Higher-level helpers are part of the target, not an afterthought
     (example: normalized seed patterns for fractal casting).
   - The return contract should remain forward-extensible rather than assuming
     we already know every primitive future systems will need.

5. Chakra recursion and determinism:
   - Recursion depth cap is 7.
   - Deterministic generation from world seed + stable IDs + rule salts.

6. Modifier precedence:
   - Closest generation parent can override, add to, or transform ancestor modifiers.
   - Grandparent modifiers are advisory unless nearest-parent rule says otherwise.

7. Attention and time:
   - Offscreen entities freeze.
   - No deferred offscreen chakra propagation for now.

8. Scale policy:
   - Behavior should be scale-invariant unless a rule explicitly opts out.

9. Detach/reattach policy:
   - Subtrees can detach and reattach while preserving full internal hierarchy/state.
   - Reattach changes graph links, not immutable identities.

10. Identity generation strategy:
    - World-generated content: deterministic from seed + recipe.
      ID format: `world:{seed_hash}:{recipe_path}:{ordinal}`.
      The ID is derived, never minted. Regenerating the same chunk with the
      same seed produces the same IDs. Extends the existing POI pattern
      (`poi:tavern_01:npc:bartender:0`).
    - Transient entities (projectiles, VFX, mirror blade clones) are still
      full entities in the same system.
      - They receive valid `entity_id` values and lifecycle state.
      - Default transient ID form is runtime-only sequential (`act{N}`) with
        no persistence entry unless the effect is explicitly promoted to a
        deterministic persistent entity.
      - They are removed via normal entity expiry/removal rules when effect TTL,
        range, or condition ends.
      - No ad-hoc special simulation path is allowed.
    - Persistence key: `entity_id` is primary for all new writes starting now.

11. Lineage state migration (completed 2026-02-17):
    - Runtime persistence and suppression are now `entity_id` keyed only.
    - Legacy `lineage_state` bridge APIs and suppression fallbacks were removed
      from active runtime paths.

12. Item stacks:
    - One entity with `quantity` scalar. Not N child entities.
    - Stacks are a rendering/UI concern, not ontological.
    - Splitting a stack creates a new entity with a new `entity_id`.

13. Equipment slots:
    - Not in Phase 1. Current flat inventory list stays.
    - Phase 1 proves attach/detach/reparent with map pickup/drop.
    - Equipment slots become socket-typed containment edges in Phase 4
      (inventory-map unification vertical slice).

14. Default chakra layouts:
    - During migration, a single core node by default. Every entity gets at minimum:
      `{chakra_id: "{entity_id}:core", channels: {hp: max_hp, mass: 1.0}, active: true}`
    - Universal channels shared by all entities / cached chakra views: `hp`, `mass`.
    - Type-specific templates available but never required.
    - Progression by entity kind:
      Simple item:  1 core node (gets slots if enchantable)
      Weapon:       1 core node (Blade weapons get segment chakras)
      Actor:        full body schema from prototype
      Building:     1 core node (expands to room chakras when entered)
      City district: 1 core node (expands to building chakras on attention)

15. Chakra channels:
    - Universal channels: `hp`, `mass`.
    - Common standardized but optional channels:
      `coherence`, `resonance`, `corruption`, `stability`, `flow`.
    - Channels allow negatives. Floats, not clamped by the substrate.
    - Clamping to [0, max] is a rule applied per-channel, not a system property.
    - Some channels are naturally negative (temperature delta, debt, corruption).

16. Rule precedence split:
    - Content rules in `chakra_rules.yaml`: which channels propagate, attenuation
      values, reducer weights, threshold bands, and any geometry-aware
      reduction logic.
    - Engine rules in code: containment invariants, recursion depth cap,
      determinism guarantees, cycle prevention. Not overridable by data.
    - Analogy: CSS cascade rules are in the engine; stylesheets are in data.

17. Non-containment edge propagation:
    - Opt-in per edge kind with explicit defaults. Schema:
      `contains`:   propagation=automatic (child channels reduce into parent)
      `owns`:       propagation=none (metadata only, no tick cost)
      `influences`: propagation=opt_in (only listed channels, per rule)
      `routes`:     propagation=opt_in
      `linked_to`:  propagation=opt_in
      `resonance`:  propagation=opt_in
    - Propagation modes are composable when rules require it.
    - `owns` edges carry no gameplay effects until Phase 5+. Metadata first.
    - Feedback loops and oscillating channel states are a known future concern;
      track them, but do not block the migration on a premature global fix.

18. Detachability constraints (v1):
    - Keep the system general: any entity is theoretically detachable.
    - Gameplay permissions are policy/data decisions, not hard engine bans.
    - Detachability is enforced by `detach_policy` data and caller authority.

19. Performance budget:
    - Target: 2ms per tick for graph/chakra processing.
    - Onscreen entities (attention budget ~2000): full chakra tick if dirty,
      skip if clean.
    - Dirty propagation only: leaf change marks ancestors dirty up to root.
      Only re-reduce dirty subtrees.
    - Collapsed entities: zero cost (one dict lookup to confirm clean).
    - Worst case math: depth 7 x branching ~10 = 10M theoretical nodes.
      Attention means ~200 entities expanded at once, average depth 3-4,
      ~2000 chakra nodes to reduce. At 1us per reduction = 2ms. Fits.

20. Spatial substrate:
    - Legacy rectangular zones are deprecated as world truth.
    - Canonical cache geometry is quadtree/attention-grid by LoD band.
    - Quadtree radix is configurable (default radix=2, not hardcoded).
    - Rectangular legacy zones may exist temporarily as compatibility caches only.

21. Multi-size entities and footprints:
    - Every entity has an absolute footprint, not just a point.
    - Runtime entity records carry explicit `footprint_local` and `footprint_abs`.
      Tag-based footprint inference is migration fallback only.
    - Footprint is a first-class input to containment, collision, interaction,
      and rendering.
    - Movement blocking is rule-driven per entity kind (data-defined), not
      hardcoded by size or band.
    - LoD bands (micro, local, regional, continental, etc.) are simulation/render
      bands, not separate ontologies.

22. Attention field and observer sources:
    - Player/camera fovea is the primary attention source.
    - Additional observer anchors (scry points, remote eyes, special entities)
      can request high-fidelity realization in distant regions.
    - "Observed = real" applies to all active observers, not only the player body.
    - If multiple foveas disagree on temperature/fidelity, take the hottest tier.

23. Global energy queue:
    - Simulation temperature model is mandatory:
      hot (full fidelity), warm (reduced cadence), cold (stochastic/lazy).
    - Important entities (kings, artifacts, quest anchors) may be promoted
      in priority even when distant.

24. Legacy cleanup protocol:
    - During migration, mark temporary bridges with
      `# [LEGACY_DELETE][ENTITY_CHAKRA]`.
    - Each such tag must be recorded in `vision_documents/spring_cleaning.txt`
      with owner and removal phase.

## Expansion and Collapse Model

The most important runtime behavior: when does a collapsed entity expand
into its full chakra subtree?

Policy: expand on attention, persist mutations, collapse on de-attention,
re-expand deterministically + apply patches.

1. A city exists as one collapsed core node in the entity graph.
2. The player approaches. The attention system triggers realization.
3. The system deterministically expands the city's recipe into
   districts -> buildings -> rooms -> contents using seed + recipe.
4. All generated child entities get deterministic IDs.
5. The persistence layer applies any stored `chakra_patch` / `tags_patch`
   entries on top of the deterministic base (player-caused mutations).
6. The player leaves. Attention de-realizes the subtree.
7. Only mutations (diffs from deterministic base) are persisted.
   The base graph is always regenerable.

This keeps:
- Save files small (only diffs stored).
- Runtime graph bounded (most of the world is collapsed).
- Determinism intact (base is always reproducible).

The fractal blade is the same pattern: blade generators ARE the expansion
recipe. Subdividing the blade expands chakra node children. The pattern
builder becomes a chakra expansion engine. The blade and the city use the
same substrate.

Open design question (explicitly deferred):

- What geometry guarantees should a collapsed entity expose when exact child
  positions lie outside attention and "observed = real" forbids fake precision?
- An approximation may be enough, but the exact contract is not yet locked.

## Edge Kind Schema

Reference table for all typed relation edges and their runtime behavior.

| Edge Kind   | Propagation | Tick Cost | Gameplay Effects | Notes                    |
|-------------|-------------|-----------|------------------|--------------------------|
| contains    | automatic   | per dirty | always           | strict tree, one parent  |
| owns        | none        | zero      | deferred (Ph5+)  | legal/control metadata   |
| influences  | opt-in      | per rule  | per rule         | explicit channel list    |
| routes      | opt-in      | per rule  | per rule         | commerce/travel/flow     |
| linked_to   | opt-in      | per rule  | per rule         | rune anchors, resonance  |
| resonance   | opt-in      | per rule  | per rule         | cross-entity harmonics   |

Default attenuation for `influences` edges: 0.5 weight.
All non-containment edges require explicit `rule_id` to propagate anything.

## Spatial Geometry and Attention Model

1. Canonical geometry:
   - World terrain and entity realization use a scale-dependent quadtree grid.
   - Legacy zone rectangles are transitional caches only.

2. Attention fovea:
   - The camera frame + nearby player context defines the primary fovea.
   - Entities in fovea are resolved to appropriate LoD and become tangible.

3. Secondary observers:
   - Scrying anchors, remote eyes, and other observer entities can create
     additional foveas.
   - Multiple active foveas must merge deterministically.

4. Realization boundary:
   - `attention.py` chooses what resolves/coarsens.
   - `aggregate_resolution.py` defines how each entity resolves/coarsens.

5. LoD bands:
   - Entities have native LoD bands with explicit render/simulation ranges.
   - Large entities can span many cache cells; tiny entities can live in very
     fine cells. Both are first-class and coexisting.

-------------------------------------------------------------------------------

## Multi-Size Footprint Interaction Contract

1. Every entity has a 2D absolute footprint (potentially degenerate for tiny items).
2. Fundamental checks use footprint overlap:
   - containment
   - blocking
   - collision
   - interaction reach
3. Cross-band interactions are allowed by default.
   - A smaller entity can affect a larger one if interaction rules permit.
   - A larger entity can affect many smaller entities via area/overlap rules.
4. Band mismatch does not prohibit interaction.
   - Rules may scale force/effect by relative size and footprint overlap.
5. Point-only checks are legacy behavior and must be tagged for deletion.

-------------------------------------------------------------------------------

## Global Energy Queue (Simulation Temperature)

1. Hot regions:
   - Full simulation cadence and detailed AI.
   - Typically within active attention fovea.

2. Warm regions:
   - Reduced cadence and simplified updates.
   - Deterministic batched steps.

3. Cold regions:
   - Stochastic/lazy updates with long intervals.
   - Still deterministic under seed + time index.

4. Priority overrides:
   - Important entities can receive higher simulation budget even if distant.
   - Priority classes are data-driven tags (`quest_critical`, `artifact`, `ruler`).

5. Queue contract:
   - Temperature affects update cadence, not ontology.
   - All updates still mutate canonical entity/chakra state.

-------------------------------------------------------------------------------

## World State Components

The minimal canonical world state is:

1. Quadtree terrain field (or equivalent cached representation).
2. World Entity Index (high-level roots, not every micro child).
3. Chakra resolution rules (data + resolver code).
4. Persistent deltas (entity and chakra mutations over deterministic base).
5. Attention field state (active foveas and LoD requirements).
6. Global energy queue state (hot/warm/cold scheduling metadata).

-------------------------------------------------------------------------------

## Delta Lifecycle

1. Resolve deterministic base from seed + recipe.
2. Apply persisted deltas.
3. Simulate and add/refine/erase deltas over time.
4. Allow delta erosion policies (for long horizons), data-driven by kind:
   - recent dropped item: low erosion
   - ambient ecology traces: higher erosion
5. Default policy: no erosion unless an entity/effect is explicitly tagged for erosion.
6. Delta erosion must be deterministic and auditable.

-------------------------------------------------------------------------------

## Save/Load Direction

1. Prototype save/load should begin once Phase 2 substrate is stable.
2. Save canonical state and deltas, not fully expanded world graphs.
3. Precompute/cache expensive terrain fields where beneficial for CPU budget.
4. Remove hacky parallel bootstrap paths as deterministic load paths mature.

## Problem Statement

Current systems still split logic across:

- map entities vs inventory entities
- legacy POI content vs entity resolver content
- actor/item logic vs site/region logic

This causes duplicate truth and blocks true fractal gameplay.

Goal: one ontology where all content is represented, simulated, and mutated
through one hierarchical entity graph plus shared geometry/relation queries.

## Runtime Rule Contracts

1. Containment operations:
   - `attach_entity(child, parent, socket)`
   - `detach_entity(child)`
   - `reparent_entity(child, new_parent, socket)`
   - Must preserve `entity_id`.
   - Only containment defines parentage, collapse scope, socket placement, and
     deterministic child ordering.

2. Geometry / composition operations:
   - The shared substrate must support operations equivalent to:
     `move_entity_geometry(target_id, dx, dy, dz)`
     `set_entity_position(target_id, x, y, z)`
     `mutate_entity_channels(target_id, delta_channels, policy)`
     `rewire_relation_edge(src, dst, edge_kind, rule)`
     `query_geometry(root_entity_id, capabilities_or_detail)`
     `query_normalized_pattern(root_entity_id, helper_options)`
   - Chakra-named wrappers may survive during migration, but they should not
     imply a second ontology.

   `chakra_component` migration rule:
   - It may remain a cache/adapter behind these calls during migration.
   - It must not become the long-term authority for identity, parentage, or
     one-off bypass semantics.

3. Reduction:
   - Parent behavior derives from child state and geometry.
   - Nearest-parent precedence applies before ancestor aggregation.
   - Reducers may inspect relative positions, edge geometry, sibling symmetries,
     and other pattern features, not only scalar channels.

4. Mutation propagation:
   - Propagation modes may be composed (`radial + upward`, etc.) when the
     content requires it.
   - Composition order and no-double-apply behavior must remain deterministic.

5. Typed relation semantics:
   - Typed relation edges may cross branches, scales, and regions.
   - They do not create parentage or multi-parent containment.
   - They never replace containment as the persistence ancestry path.
   - They only propagate when rules explicitly opt in.

6. Determinism:
   - Any generated subtree/edge set must be reproducible with same seed and IDs.

7. Footprint and interaction contracts:
   - `overlaps(a, b)` and `contains(a, b)` are canonical interaction primitives.
   - Cross-band interaction uses same primitives plus rule multipliers.
   - Point-only interaction helpers are compatibility wrappers and must be tagged.

## Testing Strategy

1. Identity tests:
   - `entity_id` never changes on detach/reattach/reparent.

2. Graph tests:
   - Containment stays acyclic.
   - Typed edges respect schema and do not alter containment invariants.

3. Chakra tests:
   - Chakra coordinates remain stable across graph rewires unless explicitly moved.
   - Nearest-parent precedence wins over ancestor defaults when configured.
   - Universal channels (`hp`, `mass`) exist on all instantiated geometry/chakra payloads.

4. Determinism tests:
   - Same seed and inputs produce identical generated graphs/reducer outputs.

5. Persistence tests:
   - Moved entities and mutated geometry/chakra state restore exactly after unload/reload.

6. Scale tests:
   - Same rule behavior at multiple scales for equivalent structures.

7. Geometry tests:
   - Footprint overlap/containment invariants hold across LoD bands.
   - Quadtree realization window selection is deterministic and camera-stable.
   - Pattern reconstruction from chakra node/edge data is deterministic.
   - Geometry-aware reducers return stable results for the same seeded layout.
   - Canonical float world positions are preserved through realization/query
     pipelines.
   - Query envelopes explicitly report realization/precision state and never
     fabricate exact geometry for collapsed or approximate subtrees.
   - Body-node `body_float_pos` migration behavior has a generic successor
     before the body-specific tag is removed.

8. Projection/view-model tests:
   - Projection helpers return stable consumer payloads without requiring
     legacy facade materialization.
   - Scene view-model helpers do not mutate runtime authority and do not
     fabricate exact geometry.

9. Authority/cache tests:
   - Inventory caches, level indexes, and similar side stores can be rebuilt
     or synchronized from graph/runtime authority and do not override graph
     truth.

10. Observer tests:
   - Secondary observer anchors create deterministic remote foveas.
   - Multiple foveas merge without duplicate realization or double simulation.

11. Energy queue tests:
   - Hot/warm/cold cadence is deterministic for same seed and ticks.
   - Priority entities receive promoted cadence without violating budgets.

10. Mutation tests:
   - Composed propagation policies apply in deterministic order.
   - A composed propagation effect does not accidentally double-apply the same
     mutation unless the rule explicitly says it should.

## Risks and Mitigations

1. Risk: Graph complexity causes hard-to-debug behavior.
   - Mitigation: strict containment invariants + debug graph inspectors.

2. Risk: Performance issues from deep recursive evaluation.
   - Mitigation: depth cap 7 + chunk budgets + cached reducer outputs.
   - Mitigation: dirty-flag propagation (only re-reduce dirty subtrees).
   - Mitigation: expansion/collapse lifecycle (most entities collapsed).
   - Budget: 2ms per tick, ~2000 active chakra nodes max.

3. Risk: Migration churn breaks quest logic.
   - Mitigation: keep semantic IDs stable and bridge to immutable entity IDs.

4. Risk: Ambiguous precedence semantics.
   - Mitigation: explicit reducer order and per-edge priority values.
   - Mitigation: engine rules (invariants) in code, content rules in data.

5. Risk: Universal system imposes too much ceremony on simple cases.
   - Mitigation: single-core-node default. A potion has one chakra node.
     Cost of opt-in is one dict entry. Complexity is progressive.

6. Risk: Non-containment edges become a surprise performance bomb.
   - Mitigation: all non-containment propagation is opt-in.
     `owns` edges have zero tick cost by default.

7. Risk: Overlay edges create feedback loops or oscillating channel behavior.
   - Mitigation: keep propagation opt-in, add reducer tracing and deterministic
     fixtures, and wait for a concrete failure mode before adding heavyweight
     general loop-control machinery.

8. Risk: Zone-to-quadtree transition causes duplicate caches or stale entities.
   - Mitigation: keep one authoritative realization index keyed by entity_id +
     quadtree cell and enforce de-duplication checks in attention staging.

## Definition of Done

This plan is complete when:

1. All world and inventory content uses the same entity graph.
2. All entities expose geometry/composition state through one model, including geometry
   rich enough for pattern queries.
3. Detach/reattach works without identity or state loss.
4. Parent behavior is derived from child state and geometry with
   nearest-parent precedence.
5. Recursion is deterministic and capped at 7.
6. Scale-invariant behavior is the default across systems.
7. Legacy split pipelines are removed.
8. Quadtree attention geometry replaces legacy zone authority.
9. Global energy queue controls far-field simulation cadence.
10. Legacy bridge tags are resolved and removed.
