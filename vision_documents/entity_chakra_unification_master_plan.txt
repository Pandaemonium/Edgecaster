## Entity + Chakra Unification Master Plan
Updated: 2026-04-18
Status: v1.37 (Phase 8 Slice XIII - game.py, dialogues.py, actions.py migrated off ensure_actor_chakra_state; only annotated legacy helper and effective_* internal fallbacks remain)

This is the execution plan for:

1. Everything with persistent gameplay identity or compositional participation is an entity.
2. "Chakra" is a role/query word for an entity within a larger hierarchy, not a second ontology.
3. The canonical organization is a strict containment tree plus expandable typed relation edges.
4. Geometry is first-class, stored canonically in absolute world space, and queryable through one shared interface.
5. Rules are scale-invariant by default.

This plan is intentionally implementation-first and absorbs the still-relevant
work that survived the earlier POI/entity unification plan.

## Current Snapshot (2026-04-13)

Implemented and stable:

1. Identity substrate:
   - `Entity` has Phase-1 fields (`entity_id`, `semantic_id`, `proto_id`,
     `lod_band`, `parent_entity_id`, `socket_id`, `chakra_component`).
   - Deterministic runtime IDs from seed + recipe + location are in use.

2. Persistence bridge:
   - `game.entity_state` exists and receives lifecycle writes.
   - Runtime removal/death/suppression now use `entity_id` only.
   - Legacy lineage write/read bridge methods were deleted from runtime codepaths.
   - Object/entity persistence writes now target the resolved `entity_id` key
     only. Legacy lineage data remains read-compat fallback rather than a peer
     write target.
   - Read compatibility now treats entity-keyed records as lifecycle- and
     ownership-authoritative; lineage may backfill old detail fields, but it
     no longer overrides suppression truth once an entity record exists.
   - Deterministic resolver/aggregate children now begin separating `eid` from
     `lineage_id` instead of treating lineage paths as runtime entity identity.
   - Unique world-root aggregates now keep historical root `eid` values for
     compatibility while using a distinct lineage namespace, so even parentless
     macro entities no longer collapse ancestry and identity into one string.
   - Attention realization no longer fabricates lineage from `eid` when a spawn
     intent omitted provenance; absence now stays absent instead of becoming a
     fake identity-shaped lineage.
   - Door state mutations now write immediate entity-state deltas in the same
     patch shape used by attention rehydration (`last_known_tags`,
     `last_known_glyph`, `last_known_blocks_movement`) instead of relying only
     on a later snapshot pass to preserve open/closed state.
   - Spawn and attention-stage paths initialize lifecycle flags in `entity_state`.

3. Footprint substrate:
   - Canonical footprint helpers exist and core occupancy/blocking checks are
     footprint-aware in spawn/AI/combat paths.

4. Inventory bridge:
   - Pickup/drop/transfer attach/detach parent/socket metadata.
   - Shared graph ops now exist for attach/detach/reparent operations.
   - Shared graph-op split now exists (`split_stack_entity`) with deterministic
     split identity + provenance tags.
   - Inventory/trade split callsites now use shared graph-op split directly.
   - Trade item moves (single + proposal flow) now route through shared
     graph transfer operations.

5. Chakra substrate kickoff:
   - Typed chakra dataclasses now exist:
     `ChakraNode`, `ChakraEdge`, `ChakraComponent`.
   - These are currently a migration surface for the unified hierarchical
     entity model, not a permanent second ontology.
   - Spawn factory now coerces YAML chakra payloads to typed components and
     guarantees a default `{entity_id}:core` node.
   - Runtime bridge now lazily initializes legacy actor chakra state via
     `ensure_actor_chakra_state(...)` in core chakra consumers.
   - Runtime state mutations now mirror back into `ChakraComponent` via
     `sync_actor_chakra_state(...)` in charge/use/edit paths.
   - Actor-scoped chakra mutation wrappers now exist:
     `unlock_actor_chakra(...)`, `toggle_actor_chakra(...)`.
   - Monk unlock flow, Chakra Sage dialogue unlock flow, and Chakra Scene toggle
     interactions now route through wrapper mutations.
   - Spawn-time actor `ChakraState` bootstrap has been removed.
   - Chakra mutation wrappers now mark the entity graph dirty when a `game`
     context is available, so reducer cache invalidation follows real runtime
     writes instead of test-only helper calls.

6. Test posture:
   - Migration-focused suites are green (inventory, spawning, POI cutover,
     attention suppression, combat/action runner, rune siege, footprints,
     chakra component bootstrap, graph ops).

7. Phase 2 lifecycle/query substrate:
   - `EntityGraphStore` now tracks lifecycle/query metadata directly on nodes:
     `lod_state`, `layout_id`, and `rule_id`.
   - `edgecaster/systems/entity_snapshots.py` is now the shared owner of
     deterministic-child snapshot persistence/apply logic.
   - `edgecaster/systems/entity_lifecycle.py` now owns resolver-backed
     expand/collapse v0 for attention-managed descendants.
   - `edgecaster/systems/entity_geometry.py` now exposes the shared geometry
     query envelope plus `query_normalized_pattern(...)`.
   - Chakra seed generation now prefers shared component geometry when an actor
     already exposes a usable `ChakraComponent`, then falls back to the legacy
     body-schema path.
   - Runtime effective chakra reads (`effective_unlocked_nodes`,
     `effective_active_nodes`, `effective_chakra_state`) now rebuild from the
     actor's `ChakraComponent` first instead of depending on cached
     `actor.chakra_state` bootstrap side effects.
   - `pattern_runtime.act_chakra(...)` now stays on the entity/component path
     for component-backed actors and skips `resolve_body_schema(...)` unless it
     is actually on a schema-only fallback path.
   - `scenes/chakra_scene.py` now passes the live `game` context into
     `PatternPreviewWidget`, so the preview path can use the shared
     entity/component seed builder instead of falling back to schema-only mode
     during normal gameplay.
   - Chakra scene helper reads now prefer cached persistent `actor.chakra_state`
     before calling the legacy compat bootstrap helper.
   - `build_chakra_generator_seed(...)` now prefers the realized body-node
     entity tree for actor anatomy, using the explicit `ChakraState` argument
     for active-node, alignment, and pattern-root semantics.
   - When the entity path is unavailable or insufficient, the seed builder now
     re-resolves authored `body_schema` on demand for actor callers that passed
     `body_schema={}`, instead of failing with a misleading root-not-found error.
   - `AttentionCellStore` now uses a hierarchical rect index keyed by
     `entity_id`, and `sync_attention_instantiation(...)` now expands/collapses
     resolver-backed parents through the lifecycle module instead of owning the
     descendant materialization pipeline inline.

8. Actor-body layered expansion kickoff:
   - `edgecaster/systems/entity_body.py` now maps authored actor anatomy into
     deterministic body-node entity specs with stable `entity_id`s derived from
     the owning actor plus dotted body-node ids.
   - `expand_entity(...)` can now realize actor/body children on `socket_id="body"`
     without staging them into the visible attention store.
   - `query_geometry(..., realize_policy="require")` now fully realizes the
     actor-body subtree for graph/query callers.

9. Reducer runtime wiring kickoff:
   - `scheduling.chakra_reducer_tick(...)` now reuses cached reduced channel
     snapshots for clean actor subtrees and only re-reduces actors whose graph
     path was marked dirty.
   - `pattern_runtime.chakra_modifiers(...)` now reads reduced charge channels
     when present, so one real gameplay consumer is on the reducer path.
   - Runtime resonance/charge evaluation no longer needs to resolve
     `body_schema` during the main tick loop; it now derives resonance from the
     active node set directly.
   - Monk level-up unlocks and Chakra Sage unlock choices now query unlockable
     chakras from deterministic body-node specs, not from a fresh
     body-schema-only traversal.

## Phase 2 Slice Batch Landed (2026-04-11)

This batch closes the next five planned substrate slices after the earlier
identity/provenance and door-persistence work.

1. Slice 2F - Graph lifecycle metadata lock
   - `EntityGraphNode` now carries `lod_state`, `layout_id`, and `rule_id`.
   - Registration helpers and major spawn/world-entry paths now populate those
     fields explicitly instead of hiding them only in tags.

2. Slice 2G - Shared runtime snapshot module
   - Snapshot/apply helpers moved into `edgecaster/systems/entity_snapshots.py`.
   - `attention.py` now delegates snapshot persistence/apply there.
   - `entity_ops.toggle_door(...)` now uses the shared persistence helper.

3. Slice 2H - Expansion / collapse lifecycle v0
   - `edgecaster/systems/entity_lifecycle.py` now exposes
     `expand_entity(...)` and `collapse_entity(...)`.
   - Scope is resolver-backed deterministic parents only, with idempotent
     direct-child realization and snapshot writeback on collapse.

4. Slice 2I - Shared geometry query API v0
   - `edgecaster/systems/entity_geometry.py` now returns the shared geometry
     envelope (`root_entity_id`, `realization_state`, `precision`, `nodes`,

## Decisions Locked In

1. Identity and persistence:
   - `entity_id` is immutable and is the primary persistence key.
   - `semantic_id` remains for quest and narrative meaning.
   - Multiple entities may share a `semantic_id` when they participate in the
     same gameplay concept.
   - `lineage_path` is contextual and may change when graph links change.

2. Spatial truth:
   - Canonical geometry is stored in absolute world space.
   - Parent-relative or local coordinate systems may be derived when useful,
     but they are adapters, not the source of truth.
   - Geometry formed by entity positions and links is canonical gameplay
     data, not renderer garnish.
   - Rune interactions, fractal growth, and future magic systems may query this
     geometry directly.
   - For now, assume all entities participate in this geometry/query surface.

3. Graph model:
   - One strict containment tree (single containment parent).
   - Additional typed graph edges allowed (`owns`, `influences`, `linked_to`, etc.).
   - Every chakra is an entity. "Chakra" describes an entity's role within a
     larger composition.
   - Current `ChakraComponent` records are a migration/cache structure, not a
     separate ontology.
   - "Owning a forest" means legal/control ownership edge, not inventory containment.

4. Query surface:
   - The shared geometry API must support raw positions/edges and richer derived
     primitives when useful.
   - Higher-level helpers are part of the target, not an afterthought
     (example: normalized seed patterns for fractal casting).
   - The return contract should remain forward-extensible rather than assuming
     we already know every primitive future systems will need.

5. Chakra recursion and determinism:
   - Recursion depth cap is 7.
   - Deterministic generation from world seed + stable IDs + rule salts.

6. Modifier precedence:
   - Closest generation parent can override, add to, or transform ancestor modifiers.
   - Grandparent modifiers are advisory unless nearest-parent rule says otherwise.

7. Attention and time:
   - Offscreen entities freeze.
   - No deferred offscreen chakra propagation for now.

8. Scale policy:
   - Behavior should be scale-invariant unless a rule explicitly opts out.

9. Detach/reattach policy:
   - Subtrees can detach and reattach while preserving full internal hierarchy/state.
   - Reattach changes graph links, not immutable identities.

10. Identity generation strategy:
    - World-generated content: deterministic from seed + recipe.
      ID format: `world:{seed_hash}:{recipe_path}:{ordinal}`.
      The ID is derived, never minted. Regenerating the same chunk with the
      same seed produces the same IDs. Extends the existing POI pattern
      (`poi:tavern_01:npc:bartender:0`).
    - Transient entities (projectiles, VFX, mirror blade clones) are still
      full entities in the same system.
      - They receive valid `entity_id` values and lifecycle state.
      - Default transient ID form is runtime-only sequential (`act{N}`) with
        no persistence entry unless the effect is explicitly promoted to a
        deterministic persistent entity.
      - They are removed via normal entity expiry/removal rules when effect TTL,
        range, or condition ends.
      - No ad-hoc special simulation path is allowed.
    - Persistence key: `entity_id` is primary for all new writes starting now.

11. Lineage state migration (completed 2026-02-17):
    - Runtime persistence and suppression are now `entity_id` keyed only.
    - Legacy `lineage_state` bridge APIs and suppression fallbacks were removed
      from active runtime paths.

12. Item stacks:
    - One entity with `quantity` scalar. Not N child entities.
    - Stacks are a rendering/UI concern, not ontological.
    - Splitting a stack creates a new entity with a new `entity_id`.

13. Equipment slots:
    - Not in Phase 1. Current flat inventory list stays.
    - Phase 1 proves attach/detach/reparent with map pickup/drop.
    - Equipment slots become socket-typed containment edges in Phase 4
      (inventory-map unification vertical slice).

14. Default chakra layouts:
    - During migration, a single core node by default. Every entity gets at minimum:
      `{chakra_id: "{entity_id}:core", channels: {hp: max_hp, mass: 1.0}, active: true}`
    - Universal channels shared by all entities / cached chakra views: `hp`, `mass`.
    - Type-specific templates available but never required.
    - Progression by entity kind:
      Simple item:  1 core node (gets slots if enchantable)
      Weapon:       1 core node (Blade weapons get segment chakras)
      Actor:        full body schema from prototype
      Building:     1 core node (expands to room chakras when entered)
      City district: 1 core node (expands to building chakras on attention)

15. Chakra channels:
    - Universal channels: `hp`, `mass`.
    - Common standardized but optional channels:
      `coherence`, `resonance`, `corruption`, `stability`, `flow`.
    - Channels allow negatives. Floats, not clamped by the substrate.
    - Clamping to [0, max] is a rule applied per-channel, not a system property.
    - Some channels are naturally negative (temperature delta, debt, corruption).

16. Rule precedence split:
    - Content rules in `chakra_rules.yaml`: which channels propagate, attenuation
      values, reducer weights, threshold bands, and any geometry-aware
      reduction logic.
    - Engine rules in code: containment invariants, recursion depth cap,
      determinism guarantees, cycle prevention. Not overridable by data.
    - Analogy: CSS cascade rules are in the engine; stylesheets are in data.

17. Non-containment edge propagation:
    - Opt-in per edge kind with explicit defaults. Schema:
      `contains`:   propagation=automatic (child channels reduce into parent)
      `owns`:       propagation=none (metadata only, no tick cost)
      `influences`: propagation=opt_in (only listed channels, per rule)
      `routes`:     propagation=opt_in
      `linked_to`:  propagation=opt_in
      `resonance`:  propagation=opt_in
    - Propagation modes are composable when rules require it.
    - `owns` edges carry no gameplay effects until Phase 5+. Metadata first.
    - Feedback loops and oscillating channel states are a known future concern;
      track them, but do not block the migration on a premature global fix.

18. Detachability constraints (v1):
    - Keep the system general: any entity is theoretically detachable.
    - Gameplay permissions are policy/data decisions, not hard engine bans.
    - Detachability is enforced by `detach_policy` data and caller authority.

19. Performance budget:
    - Target: 2ms per tick for graph/chakra processing.
    - Onscreen entities (attention budget ~2000): full chakra tick if dirty,
      skip if clean.
    - Dirty propagation only: leaf change marks ancestors dirty up to root.
      Only re-reduce dirty subtrees.
    - Collapsed entities: zero cost (one dict lookup to confirm clean).
    - Worst case math: depth 7 x branching ~10 = 10M theoretical nodes.
      Attention means ~200 entities expanded at once, average depth 3-4,
      ~2000 chakra nodes to reduce. At 1us per reduction = 2ms. Fits.

20. Spatial substrate:
    - Legacy rectangular zones are deprecated as world truth.
    - Canonical cache geometry is quadtree/attention-grid by LoD band.
    - Quadtree radix is configurable (default radix=2, not hardcoded).
    - Rectangular legacy zones may exist temporarily as compatibility caches only.

21. Multi-size entities and footprints:
    - Every entity has an absolute footprint, not just a point.
    - Runtime entity records carry explicit `footprint_local` and `footprint_abs`.
      Tag-based footprint inference is migration fallback only.
    - Footprint is a first-class input to containment, collision, interaction,
      and rendering.
    - Movement blocking is rule-driven per entity kind (data-defined), not
      hardcoded by size or band.
    - LoD bands (micro, local, regional, continental, etc.) are simulation/render
      bands, not separate ontologies.

22. Attention field and observer sources:
    - Player/camera fovea is the primary attention source.
    - Additional observer anchors (scry points, remote eyes, special entities)
      can request high-fidelity realization in distant regions.
    - "Observed = real" applies to all active observers, not only the player body.
    - If multiple foveas disagree on temperature/fidelity, take the hottest tier.

23. Global energy queue:
    - Simulation temperature model is mandatory:
      hot (full fidelity), warm (reduced cadence), cold (stochastic/lazy).
    - Important entities (kings, artifacts, quest anchors) may be promoted
      in priority even when distant.

24. Legacy cleanup protocol:
    - During migration, mark temporary bridges with
      `# [LEGACY_DELETE][ENTITY_CHAKRA]`.
    - Each such tag must be recorded in `vision_documents/spring_cleaning.txt`
      with owner and removal phase.

## Expansion and Collapse Model

The most important runtime behavior: when does a collapsed entity expand
into its full chakra subtree?

Policy: expand on attention, persist mutations, collapse on de-attention,
re-expand deterministically + apply patches.

1. A city exists as one collapsed core node in the entity graph.
2. The player approaches. The attention system triggers realization.
3. The system deterministically expands the city's recipe into
   districts -> buildings -> rooms -> contents using seed + recipe.
4. All generated child entities get deterministic IDs.
5. The persistence layer applies any stored `chakra_patch` / `tags_patch`
   entries on top of the deterministic base (player-caused mutations).
6. The player leaves. Attention de-realizes the subtree.
7. Only mutations (diffs from deterministic base) are persisted.
   The base graph is always regenerable.

This keeps:
- Save files small (only diffs stored).
- Runtime graph bounded (most of the world is collapsed).
- Determinism intact (base is always reproducible).

The fractal blade is the same pattern: blade generators ARE the expansion
recipe. Subdividing the blade expands chakra node children. The pattern
builder becomes a chakra expansion engine. The blade and the city use the
same substrate.

Open design question (explicitly deferred):

- What geometry guarantees should a collapsed entity expose when exact child
  positions lie outside attention and "observed = real" forbids fake precision?
- An approximation may be enough, but the exact contract is not yet locked.

## Spatial Geometry and Attention Model

1. Canonical geometry:
   - World terrain and entity realization use a scale-dependent quadtree grid.
   - Legacy zone rectangles are transitional caches only.

2. Attention fovea:
   - The camera frame + nearby player context defines the primary fovea.
   - Entities in fovea are resolved to appropriate LoD and become tangible.

3. Secondary observers:
   - Scrying anchors, remote eyes, and other observer entities can create
     additional foveas.
   - Multiple active foveas must merge deterministically.

4. Realization boundary:
   - `attention.py` chooses what resolves/coarsens.
   - `aggregate_resolution.py` defines how each entity resolves/coarsens.

5. LoD bands:
   - Entities have native LoD bands with explicit render/simulation ranges.
   - Large entities can span many cache cells; tiny entities can live in very
     fine cells. Both are first-class and coexisting.

## Multi-Size Footprint Interaction Contract

1. Every entity has a 2D absolute footprint (potentially degenerate for tiny items).
2. Fundamental checks use footprint overlap:
   - containment
   - blocking
   - collision
   - interaction reach
3. Cross-band interactions are allowed by default.
   - A smaller entity can affect a larger one if interaction rules permit.
   - A larger entity can affect many smaller entities via area/overlap rules.
4. Band mismatch does not prohibit interaction.
   - Rules may scale force/effect by relative size and footprint overlap.
5. Point-only checks are legacy behavior and must be tagged for deletion.

## Global Energy Queue (Simulation Temperature)

1. Hot regions:
   - Full simulation cadence and detailed AI.
   - Typically within active attention fovea.

2. Warm regions:
   - Reduced cadence and simplified updates.
   - Deterministic batched steps.

3. Cold regions:
   - Stochastic/lazy updates with long intervals.
   - Still deterministic under seed + time index.

4. Priority overrides:
   - Important entities can receive higher simulation budget even if distant.
   - Priority classes are data-driven tags (`quest_critical`, `artifact`, `ruler`).

5. Queue contract:
   - Temperature affects update cadence, not ontology.
   - All updates still mutate canonical entity/chakra state.

## World State Components

The minimal canonical world state is:

1. Quadtree terrain field (or equivalent cached representation).
2. World Entity Index (high-level roots, not every micro child).
3. Chakra resolution rules (data + resolver code).
4. Persistent deltas (entity and chakra mutations over deterministic base).
5. Attention field state (active foveas and LoD requirements).
6. Global energy queue state (hot/warm/cold scheduling metadata).

## Delta Lifecycle

1. Resolve deterministic base from seed + recipe.
2. Apply persisted deltas.
3. Simulate and add/refine/erase deltas over time.
4. Allow delta erosion policies (for long horizons), data-driven by kind:
   - recent dropped item: low erosion
   - ambient ecology traces: higher erosion
5. Default policy: no erosion unless an entity/effect is explicitly tagged for erosion.
6. Delta erosion must be deterministic and auditable.

## Save/Load Direction

1. Prototype save/load should begin once Phase 2 substrate is stable.
2. Save canonical state and deltas, not fully expanded world graphs.
3. Precompute/cache expensive terrain fields where beneficial for CPU budget.
4. Remove hacky parallel bootstrap paths as deterministic load paths mature.

## Problem Statement

Current systems still split logic across:

- map entities vs inventory entities
- legacy POI content vs entity resolver content
- actor/item logic vs site/region logic

This causes duplicate truth and blocks true fractal gameplay.

Goal: one ontology where all content is represented, simulated, and mutated
through one hierarchical entity graph plus shared geometry/relation queries.

## Target Data Contracts

### A. Entity record

- `entity_id: str` (immutable PK)
- `semantic_id: Optional[str]` (may be shared across multiple entities)
- `proto_id: str`
- `kind: str`
- `abs_x: float64`
- `abs_y: float64`
- `abs_z: float64` (optional or default 0.0)
- `footprint: {x0, y0, x1, y1}` (float64 rectangle in absolute space)
- `lod_band: str` (micro/local/regional/continental/etc.)
- `tags: dict`

### B. Entity relationships

Containment edge (strict tree):
- `child_entity_id`
- `parent_entity_id`
- `socket_id` (optional)
- `ordinal` (optional deterministic order)

Typed relation edges (graph):
- `src_entity_id`
- `dst_entity_id`
- `relation_kind` (`owns`, `influences`, `routes`, etc.)
- `weight`
- `rule_id`

### C. Geometry / composition view

Ontology rule:

- every meaningful subcomponent should eventually be representable as an entity
- during migration, code may still expose part of this through
  `chakra_component`
- that migration surface is allowed, but it is not a second ontology

Minimum queryable primitives:

- `node_or_entity_id`
- `entity_id`
- `x: float64`
- `y: float64`
- `z: float64`
- `channels: dict[str, float]`
- `active: bool`
- `tags: dict`

Relation primitive:

- `src_id`
- `dst_id`
- `edge_kind` (`contains`, `generation`, `influence`, `resonance`, etc.)
- `rule_id`
- `weight`
- `priority`
- `geometry_kind` (default `segment`; optional richer edge semantics later)
- `geometry_payload` (optional shape/control data if edge geometry is not implicit)

The shared query surface must support:

- raw nodes/edges/positions
- pattern queries
- geometry-aware reducers
- rune and fractal interactions
- richer derived primitives and helper calls when useful
  (for example normalized seed patterns)
- forward-extensible return shapes so new helpers/primitives can be added later

First-draft conceptual entry points:

- `query_geometry(root_entity_id, *, detail_level="raw", max_depth=None, include_relation_edges=True, derive=(), realize_policy="forbid")`
- `query_normalized_pattern(root_entity_id, *, helper_id="seed_pattern", realize_policy="forbid")`

Minimum result envelope:

- `root_entity_id`
- `realization_state` (`realized`, `collapsed`, or `mixed`)
- `precision` (`exact` or `approximate`)
- `nodes`
- `edges`
- `derived`
- `warnings`

Realization policy meanings:

- `forbid`: do not instantiate hidden children; return collapsed or approximate
  data plus warnings if needed
- `allow`: may realize if the runtime already has the needed data cheaply
- `require`: caller is explicitly asking for exact expanded geometry

Contract rule:

- Queries must never silently fabricate exact geometry when only approximate or
  collapsed information is available.

### D. Persistence state

- `entity_id`
- `removed`
- `dead`
- `last_known_hp`
- `tags_patch`
- `chakra_patch` (transitional name for channel/geometry diffs)
- `custom_payload`

First-draft patch envelope:

- `patch_version`
- `entity_id`
- `updated_tick`
- `state_flags`
- `tags_patch`
- `channel_patch`
- `geometry_patch`
- `relation_patch`
- `custom_payload`

`geometry_patch` may include:

- absolute position override
- footprint override
- node position overrides
- edge geometry overrides

`relation_patch` may include:

- containment parent/socket override
- typed relation additions
- typed relation removals

Lineage state remains read-compat only during migration. `entity_id` is the
authoritative persistence key.

## Runtime Rule Contracts

1. Containment operations:
   - `attach_entity(child, parent, socket)`
   - `detach_entity(child)`
   - `reparent_entity(child, new_parent, socket)`
   - Must preserve `entity_id`.
   - Only containment defines parentage, collapse scope, socket placement, and
     deterministic child ordering.

2. Geometry / composition operations:
   - The shared substrate must support operations equivalent to:
     `move_entity_geometry(target_id, dx, dy, dz)`
     `set_entity_position(target_id, x, y, z)`
     `mutate_entity_channels(target_id, delta_channels, policy)`
     `rewire_relation_edge(src, dst, edge_kind, rule)`
     `query_geometry(root_entity_id, capabilities_or_detail)`
     `query_normalized_pattern(root_entity_id, helper_options)`
   - Chakra-named wrappers may survive during migration, but they should not
     imply a second ontology.

   `chakra_component` migration rule:
   - It may remain a cache/adapter behind these calls during migration.
   - It must not become the long-term authority for identity, parentage, or
     one-off bypass semantics.

3. Reduction:
   - Parent behavior derives from child state and geometry.
   - Nearest-parent precedence applies before ancestor aggregation.
   - Reducers may inspect relative positions, edge geometry, sibling symmetries,
     and other pattern features, not only scalar channels.

4. Mutation propagation:
   - Propagation modes may be composed (`radial + upward`, etc.) when the
     content requires it.
   - Composition order and no-double-apply behavior must remain deterministic.

5. Typed relation semantics:
   - Typed relation edges may cross branches, scales, and regions.
   - They do not create parentage or multi-parent containment.
   - They never replace containment as the persistence ancestry path.
   - They only propagate when rules explicitly opt in.

6. Determinism:
   - Any generated subtree/edge set must be reproducible with same seed and IDs.

7. Footprint and interaction contracts:
   - `overlaps(a, b)` and `contains(a, b)` are canonical interaction primitives.
   - Cross-band interaction uses same primitives plus rule multipliers.
   - Point-only interaction helpers are compatibility wrappers and must be tagged.

## Testing Strategy

1. Identity tests:
   - `entity_id` never changes on detach/reattach/reparent.

2. Graph tests:
   - Containment stays acyclic.
   - Typed edges respect schema and do not alter containment invariants.

3. Chakra tests:
   - Chakra coordinates remain stable across graph rewires unless explicitly moved.
   - Nearest-parent precedence wins over ancestor defaults when configured.
   - Universal channels (`hp`, `mass`) exist on all instantiated geometry/chakra payloads.

4. Determinism tests:
   - Same seed and inputs produce identical generated graphs/reducer outputs.

5. Persistence tests:
   - Moved entities and mutated geometry/chakra state restore exactly after unload/reload.

6. Scale tests:
   - Same rule behavior at multiple scales for equivalent structures.

7. Geometry tests:
   - Footprint overlap/containment invariants hold across LoD bands.
   - Quadtree realization window selection is deterministic and camera-stable.
   - Pattern reconstruction from chakra node/edge data is deterministic.
   - Geometry-aware reducers return stable results for the same seeded layout.

8. Observer tests:
   - Secondary observer anchors create deterministic remote foveas.
   - Multiple foveas merge without duplicate realization or double simulation.

9. Energy queue tests:
   - Hot/warm/cold cadence is deterministic for same seed and ticks.
   - Priority entities receive promoted cadence without violating budgets.

10. Mutation tests:
   - Composed propagation policies apply in deterministic order.
   - A composed propagation effect does not accidentally double-apply the same
     mutation unless the rule explicitly says it should.

## Risks and Mitigations

1. Risk: Graph complexity causes hard-to-debug behavior.
   - Mitigation: strict containment invariants + debug graph inspectors.

2. Risk: Performance issues from deep recursive evaluation.
   - Mitigation: depth cap 7 + chunk budgets + cached reducer outputs.
   - Mitigation: dirty-flag propagation (only re-reduce dirty subtrees).
   - Mitigation: expansion/collapse lifecycle (most entities collapsed).
   - Budget: 2ms per tick, ~2000 active chakra nodes max.

3. Risk: Migration churn breaks quest logic.
   - Mitigation: keep semantic IDs stable and bridge to immutable entity IDs.

4. Risk: Ambiguous precedence semantics.
   - Mitigation: explicit reducer order and per-edge priority values.
   - Mitigation: engine rules (invariants) in code, content rules in data.

5. Risk: Universal system imposes too much ceremony on simple cases.
   - Mitigation: single-core-node default. A potion has one chakra node.
     Cost of opt-in is one dict entry. Complexity is progressive.

6. Risk: Non-containment edges become a surprise performance bomb.
   - Mitigation: all non-containment propagation is opt-in.
     `owns` edges have zero tick cost by default.

7. Risk: Overlay edges create feedback loops or oscillating channel behavior.
   - Mitigation: keep propagation opt-in, add reducer tracing and deterministic
     fixtures, and wait for a concrete failure mode before adding heavyweight
     general loop-control machinery.

8. Risk: Zone-to-quadtree transition causes duplicate caches or stale entities.
   - Mitigation: keep one authoritative realization index keyed by entity_id +
     quadtree cell and enforce de-duplication checks in attention staging.
