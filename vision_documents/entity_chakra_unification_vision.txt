## Edgecaster Vision: One Hierarchical Entity Substrate
Updated: 2026-04-11
Status: North Star (Design Lock v1.4, Phase 1 Contract Lock)

This document defines the target architecture where:

1. Everything with persistent gameplay identity or compositional participation is an entity.
2. "Chakra" is not a second thing-type; it names an entity's role as a subcomponent in a larger hierarchy.
3. Parent behavior at every scale composes upward from child entity state and geometry.
4. Geometry is first-class and mechanically meaningful.
5. Fractal recursion is first-class and deterministic.

This is intended as the canonical guide for future content, systems, and refactors.

-------------------------------------------------------------------------------

## Core Thesis

Edgecaster should be modeled as a recursive entity ecology:

- World -> region -> city -> district -> block -> building -> room -> object -> actor
- Every meaningful level is an entity
- "Chakra" means an entity viewed as part of a larger composed whole
- Parent behavior is derived from child state
- Parent and child geometry are part of the same truth, not presentation garnish
- Observation selects fidelity, not truth

This unifies content, simulation, rendering, and quest logic under one ontology.

-------------------------------------------------------------------------------

## Non-Negotiable Principles

1. Everything with persistent gameplay identity or compositional participation is an entity.
   - Forests, cities, weather cells, lairs, rune anchors, NPCs, dropped loot,
     walls, chakras, and other persistent/interactable world structures.
   - Inert substrate that has no meaningful identity or compositional participation
     does not need to be entity-backed unless gameplay later demands it.
   - No pseudo-entity side pipelines for "special" world things.

2. There is one ontology, not two.
   - Every chakra is an entity.
   - "Chakra" is a role word for an entity inside a larger composition.
   - Current runtime structures may still store some of this in
     `chakra_component`, but that is a migration surface, not a separate class
     of being.

3. Absolute space is truth.
   - Coordinates are canonical in world/absolute space.
   - Zone/chunk structures are caches for performance only.
   - Other coordinate systems may be derived for convenience, but absolute world
     space is the source of truth.

4. Identity is triple-layered.
   - `entity_id` (immutable PK) for persistence and graph membership.
   - `semantic_id` for gameplay meaning (quest/rumor/map marker).
     Multiple entities may share a semantic ID when they participate in the
     same gameplay concept.
   - `lineage_path` for contextual position in the containment tree (changes
     on reparent; not a persistence key).

5. Observed = real.
   - If it is observed and simulated, outcomes are canonical.
   - No fake preview entities that disagree with gameplay truth.

6. Determinism by seed.
   - Same world seed + same lineage + same choices => same outcomes.

7. Geometry is canonical.
   - Entity placement relative to related entities is part of gameplay truth.
   - Containment and typed relation links define patterns, not just inheritance.
   - The same geometry that matters for body magic must also be available
     for sites, structures, items, organizations, and other recursive entities.

## Terminology Lock

Use these terms consistently:

- `entity`: any persistent gameplay thing or meaningful subcomponent
- `chakra`: an entity considered in its role within a larger hierarchy
- `containment tree`: the single-parent parent/child structure that gives the
  world its primary composition
- `typed relation edge`: any non-containment link such as `owns`,
  `influences`, `routes`, or `linked_to`

This means:

- every chakra is an entity
- every meaningful subcomponent should eventually be representable as an entity
- richer behavior should come from the tree plus typed edges, not from adding a
  second ontological layer
- `chakra_component` may remain a useful runtime/cache structure during
  migration, but the design target is still one hierarchical entity substrate

## Canonical Entity Model

Every runtime thing conforms to one conceptual model:

- `entity_id: str` (immutable PK, deterministic for world content, sequential for transient)
- `semantic_id: Optional[str]`
- `proto_id: str`
- `kind: str` (site, actor, item, structure, effect, ecology, etc.)
- `abs_position / abs_footprint`
- `parent_entity_id: Optional[str]`
- `relation_edges`
- `tags: dict`
- current migration bridge: `chakra_component: ChakraComponent`

`chakra_component` remains a practical migration surface for now, but it should
be understood as a geometry/composition cache over the entity hierarchy, not as
proof of a separate ontology.

Current minimum shape:

- `layout_id: str` (which chakra topology this entity uses)
- `rule_id: str` (how child state is reduced to parent state)
- `depth: int` (recursion depth)
- `channels: dict[str, float]`
- `active_nodes: list[str]`
- `child_links: list[entity_id]`
- `geometry_links: list` (edge geometry / spatial relation data for chakra patterns)
- `derived_tags: dict` (cached behavior outputs)

Geometry is part of the substrate:

- Chakra-bearing entities must have enough positional and linkage data to
  recover the pattern formed by the entity and its chakra graph.
- This geometry is not cosmetic. It exists so rune logic, fractal growth,
  spatial reducers, and later magic systems can reason about actual shape.
- If a body, city, blade, or shrine has chakras, the system should be able to
  ask what pattern those chakras form.

### Identity Generation

Two ID spaces, one bright line:

- World-generated content: deterministic from seed + recipe.
  Format: `world:{seed_hash}:{recipe_path}:{ordinal}`.
  Regenerating the same chunk with the same seed produces identical IDs.
  Persistence stores diffs (patches) on top of the deterministic base.

- Transient entities (projectiles, VFX, summons): runtime-only sequential
  IDs (`act{N}`). No persistence entry. If something needs to survive
  save/load, it must use a deterministic ID instead.

Entity IDs are stable even if containment changes.
Reparenting changes `lineage_path` and contextual meaning, not `entity_id`.
If an arm is severed from one actor and attached to another, the game should
still remember the arm's identity and provenance while allowing it to function
as part of the new parent's chakra graph.

### Default Chakra Layout

The system is trivially cheap to opt into and progressively richer:

- During migration, every entity gets at minimum one core self-representation:
  `{chakra_id: "{entity_id}:core", channels: {hp: max_hp, mass: 1.0}, active: true}`
- A potion may remain one node. A sword may expose several composed entities or
  cached geometry nodes. An actor may expand into a full body hierarchy. A city
  expands into neighborhoods.
- Unrealized entities have collapsed composition state. A building you have never
  entered is one node. Walking in triggers deterministic expansion from
  its recipe. This is how the graph stays bounded.

Universal channels:

- `hp`
- `mass`

These are expected on all entities and on any cached geometry/chakra view that
stands in for them.

## Chakra Channels

Use a hybrid channel strategy:

Common channels (engine-level, standardized but not mandatory on every entity):

- `coherence`
- `resonance`
- `corruption`
- `stability`
- `flow`

Extension channels (content-level, optional):

- Arbitrary keys per faction/site/system (example: `fear`, `trade_flux`, `ritual_heat`)

Channel value policy:

- Channels are floats. Negatives are allowed.
- Clamping is a rule applied per-channel, not a substrate property.
  Some channels are naturally negative (temperature delta, debt, corruption
  reduction). The substrate stores what the rules produce.
- Stack quantities use `channels["quantity"]` (one entity, not N children).

Rationale:

- Universal channels keep the minimum substrate shared.
- Common channels keep cross-system behavior consistent where relevant.
- Extension channels preserve design freedom.
- Unclamped substrate prevents rules from fighting the storage layer.

## Geometry and Query Contract

Unification is not just about shared stats and shared inheritance.
It is also about shared geometry and shared access to that geometry.

The system must support:

- the position of an entity relative to its subcomponents
- the position of subcomponents relative to each other
- the links between them as meaningful geometric edges
- pattern queries over those positions and links

This matters because:

- a monk's body creates fractal patterns from bodily chakras
- a blade's segments create patterns through subdivision and linkage
- a site's parts may create runic or ritual geometry
- future magic systems may care about the pattern created by the connected
  entities in a graph, not just their scalar channel totals

If geometry is stripped away and only scalar channels remain, the ontology is
not truly unified.

The shared query surface should:

- expose raw positions and typed edges
- expose richer derived primitives when needed
- support higher-level helpers as well as raw geometry access
- remain forward-extensible rather than pretending the first version of the
  return schema will include every useful primitive forever

Examples of richer helpers/primitives that may exist now or later:

- segments
- centroids
- convex hulls or footprints
- symmetry axes
- normalized seed patterns for fractal casting
- other derived pattern metadata as systems demand it

### First-Draft Shared Query API

Conceptual entry points:

- `query_geometry(root_entity_id, *, detail_level="raw", max_depth=None, include_relation_edges=True, derive=(), realize_policy="forbid")`
- `query_normalized_pattern(root_entity_id, *, helper_id="seed_pattern", realize_policy="forbid")`

`query_geometry(...)` should return a forward-extensible payload with at least:

- `root_entity_id`
- `realization_state` (`realized`, `collapsed`, or `mixed`)
- `precision` (`exact` or `approximate`)
- `nodes`
- `edges`
- `derived`
- `warnings`

Minimum node fields:

- `node_or_entity_id`
- `entity_id`
- `abs_position`
- `channels`
- `active`
- `tags`

Minimum edge fields:

- `src_id`
- `dst_id`
- `edge_kind`
- `weight`
- `geometry_kind`
- `geometry_payload`

Realization policy meanings:

- `forbid`: must not instantiate hidden children; may return collapsed or
  approximate geometry plus warnings
- `allow`: may realize if the runtime already has the needed data cheaply
- `require`: caller is asking for exact expanded geometry and accepts the cost

Contract rules:

1. Queries must never silently fabricate exact geometry when only an
   approximation is known.
2. Callers must tolerate missing derived helpers and future-added fields.
3. Higher-level helpers are first-class, but they are helpers layered over the
   same shared substrate, not a separate path.
4. `query_normalized_pattern(...)` is the intended bridge for systems such as
   fractal casting that want a canonical helper instead of raw graph assembly.

## Fractal Chakra Recursion

Recursion is explicit and bounded.

Rules:

1. Max recursion depth is 7.
2. Child generation is deterministic:
   - seed = hash(world_seed, lineage_id, rule_id, depth, slot)
3. Child lineage IDs are deterministic paths from parent lineage.
4. Cycles are forbidden in generated lineage graphs.

If a rule attempts to recurse beyond depth 7, it must clamp gracefully and
emit terminal nodes only.

-------------------------------------------------------------------------------

## Parent-From-Children Behavior

Parents do not own "magic hidden behavior."
Parents derive behavior from child chakra state through rule reducers.

Reducer pipeline:

1. Gather child channel vectors.
2. Apply weighted transforms by child role and geometry.
3. Apply rule-specific transforms (amplify, dampen, invert, threshold).
4. Produce parent channel vector.
5. Map parent channel bands to `derived_tags`.

Reducers may inspect:

- scalar channels
- child roles
- relative positions
- graph geometry
- sibling patterns and symmetries

Example outcomes:

- High `corruption` + low `stability` -> increased spawn pressure.
- High `coherence` + high `resonance` -> stronger anchor dampening.
- High `flow` in district graph -> NPC commerce routing bonus.

## Universal Mutation Model (Most General)

All gameplay effects mutate chakra state through one mutation envelope:

- `mutation_id`
- `source_lineage_id`
- `target_selector`
- `delta_channels: dict[str, float]`
- `duration_policy` (instant, decay, timed)
- `propagation_policy`
- `determinism_salt`

Target selector options:

- Direct lineage id
- Semantic id query
- Spatial query (radius/shape)
- Rule query (all nodes with tag X)

Propagation policies are composable:

- `local` (target only)
- `upward` (toward ancestors)
- `downward` (toward descendants)
- `radial` (spatial neighbors)
- `fractal_echo` (depth-linked resonance hops)

One mutation may use more than one propagation mode when the content or rule
calls for it. This model is the most general because local-only behavior is a
strict subset.

## Expansion and Collapse Lifecycle

The central runtime question: when does a collapsed entity expand into
its full composed subtree?

Policy: expand on attention, persist mutations, collapse on de-attention,
re-expand deterministically + apply patches.

Lifecycle:

1. A city exists as one collapsed core node in the entity graph.
2. Player approaches. Attention system triggers realization.
3. System deterministically expands the city's recipe into
   districts -> buildings -> rooms -> contents using seed + recipe.
4. All generated child entities get deterministic IDs.
5. Persistence layer applies stored `chakra_patch` / `tags_patch`
   (player-caused mutations) on top of the deterministic base.
6. Player leaves. Attention de-realizes the subtree.
7. Only mutations (diffs from deterministic base) are persisted.
   The base graph is always regenerable.

This keeps save files small, the runtime graph bounded, and
determinism intact.

The fractal blade is the same pattern: blade generators ARE the
expansion recipe. Subdividing the blade expands child entities / cached
geometry nodes.
The pattern builder becomes a chakra expansion engine. When the blade
and the city use the same substrate, the unification is real.

Open design question (explicitly deferred):

- What geometry guarantees should a collapsed entity expose when exact child
  positions lie outside attention and "observed = real" forbids fake precision?
- An approximation may be enough, but the exact contract is not yet locked.

-------------------------------------------------------------------------------

## Simulation and Attention

Attention and chakra composition must cooperate:

1. Attention controls realization fidelity per camera chunk.
2. Offscreen entities freeze. No deferred offscreen propagation.
3. Persistent composition/chakra state never disappears when entities unload.
4. Re-entry restores exact prior state from entity persistence.
5. Dirty-flag propagation: leaf mutation marks ancestors dirty.
   Only dirty subtrees are re-reduced. Clean subtrees cost zero.

No renderer-driven spawning logic.
Resolver/staging may instantiate based on attention, but simulation deltas are
committed only via action/time systems.

Performance target: 2ms per tick for graph/chakra processing.
~2000 active chakra nodes in attention window at any time.
Collapsed entities (the vast majority of the world) cost zero ticks.

Concern to track:

- overlay graph feedback loops and oscillating channel behavior may become a
  problem as more `influences`, `routes`, and `linked_to` rules are added.
- Do not overdesign this early, but keep it visible as a future systems risk.

-------------------------------------------------------------------------------

## Persistence Contract

`entity_id`-keyed persistence is source of truth for mutation durability.
`lineage_state` remains as a compatibility adapter during migration but
all new writes target `entity_id`.

Required fields (conceptual):

- `entity_id` (primary key)
- `semantic_id`
- `removed`
- `dead`
- `last_known_hp`
- `tags_patch`
- `chakra_patch` (transitional name for channels/geometry state diffs from deterministic base)
- `custom_payload`

Rules:

1. Writes happen immediately on meaningful state changes.
2. Resolver checks persistence before spawn/realization.
3. Removed/dead/destroyed entities never respawn unless explicitly resurrected.
4. Only diffs from the deterministic base are stored.
   The base is always regenerable from seed + recipe.

First-draft patch envelope:

- `patch_version`
- `entity_id`
- `updated_tick`
- `state_flags` (`removed`, `dead`, other lifecycle flags)
- `tags_patch`
- `channel_patch`
- `geometry_patch`
- `relation_patch`
- `custom_payload`

`geometry_patch` may include:

- absolute position override
- footprint override
- node position overrides
- edge geometry overrides

`relation_patch` may include:

- containment parent/socket override
- typed relation additions
- typed relation removals

Migration naming rule:

- `chakra_patch` remains the legacy persisted field name during migration
- semantically it should be read as a composition/geometry patch, not as proof
  that chakras are a second ontology
- do not introduce a second competing patch format unless migration forces it

Persistence precision rule:

- If exact child geometry is unknown because a subtree is collapsed, persist
  only the exact changes that are known.
- Never persist fabricated exact positions for off-attention children.

## Relation Semantics Contract

Containment and typed relation edges do different jobs and should stay clearly
separated.

Containment edge responsibilities:

- defines the single parent in the hierarchy
- defines expansion/collapse scope
- defines socket placement and deterministic child ordering
- provides the default upward composition path
- changes when an entity is detached, reattached, equipped, or moved

Typed relation edge responsibilities:

- adds cross-links such as `owns`, `influences`, `routes`, `linked_to`,
  `resonance`
- may connect across branches, scales, or regions
- never creates parentage or multi-parent containment
- never becomes the primary persistence ancestry path
- only propagates when rules explicitly opt in

Rule of thumb:

- If removing the relation should change "what this thing is inside of", it is
  a containment edge.
- If removing the relation should change interaction without changing parentage,
  it is a typed relation edge.

-------------------------------------------------------------------------------

## ChakraComponent During Migration

`chakra_component` is allowed to remain as a practical runtime/cache structure
while the refactor is in flight, but it has strict limits.

Allowed:

- caching geometry/composition views derived from the authoritative hierarchy
- carrying transitional channel/node data for older systems
- serving as the implementation surface behind shared query helpers

Not allowed:

- becoming the authoritative source of identity
- becoming the authoritative source of parentage or containment
- accumulating bespoke gameplay semantics that bypass the shared query/mutation
  interfaces

Migration intent:

- the authoritative model is the hierarchical entity graph plus persisted
  patches and deterministic recipes
- `chakra_component` should become regenerable from that source of truth
- new systems should prefer shared query/mutation helpers over bespoke direct
  spelunking through component internals

## System Responsibilities

`systems/aggregate_resolution.py`

- Deterministic child intent generation.
- Child graph generation and lineage construction.
- Parent reducer evaluation (or reducer dispatch).

`systems/attention.py`

- Chunk-window realization/eviction orchestration.
- No content-specific composition semantics.

`systems/chakras.py`

- Geometry graph math utilities and reusable reducer primitives.
- Channel operations, merge rules, decay helpers.

`systems/scheduling.py`

- Time-step application for channel decay, pulses, and staged propagation.

Quest/dialogue systems:

- Bind to semantic IDs and read derived outcomes.
- Never bypass lineage persistence.

## Content Authoring Model

Add two content assets:

1. `content/chakra_layouts.yaml`
   - Defines node graphs/topologies per entity family or site family.
   - Includes enough positional/linkage data to recover meaningful geometry.

2. `content/chakra_rules.yaml`
   - Defines reducers, thresholds, propagation defaults, recursion behavior,
    and any geometry-aware reduction logic.

Entity/site prototypes reference:

- `chakra.layout_id`
- `chakra.rule_id`
- Optional channel defaults and role tags.

## Migration Plan (Pragmatic)

Phase 0: Schema introduction

- Add chakra component schema and loader validation.
- No behavior change yet.

Phase 1: Vertical slice (Starttsgard)

- City -> building -> room/object chakra chain.
- Validate deterministic lineage + exact restoration on unload/reload.

Phase 2: Quest chain adoption

- Inventor workshop, destabilizer ruin, failing rune migrated to chakra-backed entities.
- Semantic quest flow unchanged.

Phase 3: Rune anchor deepening

- Rune anchors use full parent-from-children channel behavior.
- Coherence and resonance crystal effects become explicit mutation packets.

Phase 4: Large POI stress test

- Colosseum or equivalent multi-zone site with per-chunk chakra realization.
- Validate performance and deterministic persistence.

Phase 5: Legacy deletion

- Remove obsolete POI special-case pipelines.
- Enforce one entity+chakra path.

## Guardrails and Test Requirements

Determinism tests:

- Same seed + same inputs => identical lineage graph and channel/geometry outputs.

Persistence tests:

- Destroyed/looted/dead state persists across unload/reload.
- Chakra mutations persist exactly.

Recursion tests:

- Depth never exceeds 7.
- No cyclic lineage generation.

Attention tests:

- Realization and eviction do not alter canonical composition state unexpectedly.

## Graph Edge Semantics

Containment edges form a strict tree. All other edge types are a graph overlay.

| Edge Kind   | Propagation | Tick Cost | Notes                          |
|-------------|-------------|-----------|--------------------------------|
| contains    | automatic   | per dirty | strict tree, single parent     |
| owns        | none        | zero      | metadata only until Phase 5+   |
| influences  | opt-in      | per rule  | explicit channel list required  |
| routes      | opt-in      | per rule  | commerce, travel, flow         |
| linked_to   | opt-in      | per rule  | rune anchors, resonance links  |

Non-containment edges never propagate unless a rule explicitly opts in.
This prevents the graph from becoming a performance bomb.

Known concern:

- As overlay edges become richer, feedback loops and oscillating channel states
  may emerge. Track this as a systems risk and solve it when the concrete
  failure mode appears.

## Detachability Policy

Not all entities can be detached from their containment parent.

| Kind       | Detach Policy | Notes                              |
|------------|---------------|------------------------------------|
| world      | never         | structural scaffolding             |
| continent  | never         | structural scaffolding             |
| region     | never         | structural scaffolding             |
| city       | admin_only    | quest/event can, player cannot     |
| district   | event_only    | destruction, conquest              |
| building   | gameplay      | demolish, relocate                 |
| room       | gameplay      |                                    |
| item       | free          |                                    |
| actor      | free          | can reparent between locations     |

Enforced via `detach_policy` on entity kind schema.

## Anti-Patterns to Ban

1. Hardcoded behavior branches by specific POI/NPC IDs in orchestration layers.
2. Renderer inventing gameplay entities.
3. Separate "special simulation paths" that bypass the unified hierarchical entity model.
4. State changes without lineage persistence writes.
5. Recursive generation without deterministic seeds and depth checks.

## Definition of Done (Vision Complete)

Edgecaster satisfies this vision when:

1. All world content is entity-backed.
2. All meaningful subcomponents are representable through the same hierarchical
   entity model, whether or not a temporary `chakra_component` cache still exists.
3. Parent behavior at all scales is derived from child state and geometry.
4. Recursive generation is deterministic and depth-bounded to 7.
5. Persistence and attention preserve exact state with no ontology split.
6. Legacy POI special-case systems are removed or reduced to compatibility stubs.

At that point, "fractal rogue-like" is not just theme. It is the engine.

## Why This Matters: One Mechanic at Every Scale

When the unification is complete, the player's existing interactions
generalize to every scale:

- "Activate a body chakra" (unlock hand -> unlock fingers) is the same
  mechanic as "activate a building's chakra" (unlock the sealed basement).
- "Subdivide a blade segment" (fractal generator expands geometry) is the
  same mechanic as "a city district spawning new buildings" (recipe expands
  containment tree).
- "Resonance bonus from bilateral arms" (two active siblings boost parent)
  is the same mechanic as "two allied districts strengthen a city wall"
  (sibling chakra channels reduce into shared parent).
- "Corrupt a rune anchor" (mutate channels, propagate upward) is the same
  mechanic as "corrupt a neighborhood" (mutate channels, derived tags shift
  NPC behavior and spawn pressure).

The player learns one interaction language and discovers it works everywhere.
That is the fractal promise.
